# Бэклог продукта

Этот файл фиксирует открытые вопросы и задачи по развитию продукта, которые ещё
не решены и не запланированы в конкретную версию. Записи здесь — повод для
решения владельца, а не принятое решение.

- Комментарий должен объяснять причину, ограничение, неочевидный контракт или
  риск, а не пересказывать соседний код.

## Открытые вопросы

### Автоматическая карта возможностей продукта

Классификация полной проверки теперь машинно связывает каждую собственную роль,
навык и инструкцию с видом участия и этапом. Она не является общим каталогом
продукта и не описывает все результаты ролей или источники поставки для
пользовательской документации.

README и справочник ролей всё ещё могут разойтись с фактическим составом после
следующего изменения. Нужно решить, следует ли расширить существующую
классификацию или создать из неё производный каталог «роль — навыки — результат
— источник поставки» и сверять с ним пользовательскую документацию в
`apm run tests`.

Задача закрыта, когда выбран единственный источник истины, проверка обнаруживает
добавленную или удалённую роль и навык, а README остаётся кратким
пользовательским входом, а не выгрузкой внутреннего каталога.

### Практические сценарии по типам задач

После быстрого старта README показывает один общий пример. Новому пользователю
всё ещё приходится самостоятельно формулировать первую задачу для требований,
архитектуры, безопасности, UX, корпуса знаний и проверки готового результата.
Нужно проверить, сократит ли отдельная страница с короткими сценариями время до
первого полезного результата без требования выбирать внутренние роли и навыки.

До создания страницы следует определить основные задачи по данным обращений или
пользовательской проверке. Иначе примеры могут закрепить случайный маршрут.

### Матрица глубины поддержки методологий

README перечисляет методологии и подходы, но не различает полный рабочий
процесс, отдельный проверочный проход и набор понятий в справках навыка. Нужно
решить, полезна ли пользователю матрица с областью применения, входами,
результатом, ограничениями и уровнем поддержки для Scrum, The Twelve-Factor App,
Clean Architecture, C4, STRIDE и других названных подходов.

Матрица не должна обещать сертификацию или соответствие стандарту. Её следует
создавать только вместе с автоматической проверкой связи с фактическими
навыками, чтобы не завести ещё один дрейфующий каталог.

### Дрейф прямой dev-зависимости в APM 0.24

В воспроизведённом проекте APM 0.24 разрешил прямую dev-зависимость
`mekras/ai-dev-team` до версии 0.20.4 и записал её в lock-файл, но
`apm audit --ci` сообщил, что активных зависимостей нет, назвал сам пакет
осиротевшим и обнаружил дрейф развёрнутого `ait-setup`. В результате клиент
загрузил старую копию навыка, хотя lock-файл содержал новую версию.

Нужно отдельно воспроизвести установку в чистом проекте с обычной зависимостью и
с `--dev`, определить, является ли причина дефектом APM, миграцией старой
установки или неправильным сценарием подключения, затем исправить первичный
механизм. Задача закрыта, когда после установки `apm audit --ci` проходит, хэш
активного `ait-setup` соответствует разрешённому пакету, а повторная настройка
не загружает старую копию.

### Завершение перепроверки проекта после обновления APM

Текущий проход охватил функциональные требования `ФТ-1`–`ФТ-11`, атрибуты
качества `КАЧ-1`–`КАЧ-6`, правила `ПР-1`–`ПР-6`, пользовательские требования
`ПТ-1`–`ПТ-4` и бизнес-требования `БТ-1`–`БТ-3`. До завершения прохода нужно
выполнить оставшиеся запланированные действия.

1. По полученному разбросу передать владельцу выбор числа повторов, допустимого
   разброса и числовых порогов пригодности.
2. После закрытия отдельных требований провести итоговую проверку связей от
   концепции и бизнес-требований до пользовательских, функциональных и
   качественных требований, правил, ограничений, реализации и проверок.
3. Перед приёмкой результата выполнить `apm run tests`, повторную установку из
   файла блокировки и `apm audit --ci`; проверить журнал изменений и передать
   владельцу артефакты, доказательства, ограничения и остаточные риски.

Задача закрыта, когда сквозной и сравнительный наборы воспроизводимо
запускаются, итоговая проверка связей не находит необъяснённых разрывов, а
обязательные проверки проходят без ошибок.

### Подавления операционной проверки корпуса

Операционная проверка корпуса на 24 июля 2026 года не находит ошибок договора,
блокеров и предупреждений качества. Политика содержит 630 документированных
подавлений срабатываний. Нужно решить, достаточно ли оснований в политике для
сохранения каждого класса подавлений и требуется ли периодический пересмотр при
изменении источников.

Задача закрыта, когда владелец подтвердит критерий пересмотра, а проверка будет
отличать устаревшее подавление от актуального исключения без повторного вывода
найденных значений в отчёт.

### Сквозная проверка целостного контура

Команда `apm run product-evals` и сценарий `catalog-import-policy` реализуют
сквозной путь от свободного запроса через решение владельца до передачи
проверяемого артефакта на приёмку. Средство отдельно запускает клиент без
`ai-dev-team`, текущее рабочее дерево и предыдущий принятый выпуск, затем
сохраняет наблюдаемый след в `local/product-evals/`.

Для проверки бизнес-эффекта из `БТ-2` набор должен поддерживать два сравнения: с
тем же клиентским инструментом без `ai-dev-team` и с предыдущей принятой версией
продукта. В одинаковых условиях нужно измерять обязательные пропуски,
неправомерные решения агента, готовность результата к приёмке, возвраты на
доработку и критические нарушения. Время выполнения и расход токенов фиксируются
отдельно и не компенсируют ухудшение качества.

Шесть калибровочных запусков выполнены. Ранние прогоны помогли исправить
изоляцию, двусмысленность запроса, смысловые пути артефактов и завершающую
проверку результата. Последний запуск 2026-07-26 сравнил текущее дерево с тем же
клиентом без продукта и с принятым выпуском `0.21.3`. Критических нарушений не
было. Текущее дерево не пропустило обязательных действий и достигло статуса
готовности к приёмке. Вариант без продукта пропустил пять действий, а `0.21.3` —
три. Один повтор по-прежнему даёт только калибровочное наблюдение. Владелец
выбирает:

- число повторов, допустимый разброс и числовые пороги.

До этого нельзя заявлять процент улучшения. Для вывода о стоимости целевой
проект должен отдельно предоставить данные о времени повторной работы, поздних
исправлениях или других последствиях. Без этих данных подтверждаются только
наблюдаемые показатели риска.

### Настольные интерфейсы

Первый профиль интерфейсного слоя продукта покрывает Android, iOS и веб.
Windows, GNOME, KDE и другие настольные платформы нужно добавить отдельным
решением: завести релевантные источники корпуса, определить платформенные
правила, проверить границы с локальными правилами целевых проектов и расширить
`ait-interface-design` постоянными проверками.

### Развитие слоя согласования понятий

Введён слой согласования понятий `knowledge/concepts.yml` (решение —
`docs/adr/0001-concepts-reconciliation-layer.md`), пока в виде MVP с несколькими
засеянными понятиями. Осталось:

- проверка целостности ссылок слоя (`defined_by`, `covered_in`) в
  `kc-validation`, чтобы слой не дрейфовал; сейчас это вне продукта (валидатор в
  коллекции корпуса);
- расширение охвата по требованию (новые сквозные понятия и коллизии);
- решение, нужен ли отдельный продуктовый канон терминов (связка с `ru-lang`)
  поверх корпусного слоя.
