# UC-USR-001. Оценить состояние проекта

Игорь хочет иметь профессионально обоснованное представление о состоянии проекта
для ближайшего решения, не выполняя самостоятельно работу всех специалистов. Он
поручает агентам подобрать и выполнить подходящую проверку.

- Статус: **принят для реализации**
- Уровень: **[цель пользователя](README.md)**
- Область действия: **[ai-dev-team](../../01-concept/README.md)**

## Действующие лица и их интересы

Основное действующее лицо: **[Игорь](../personas/igor.md)**

- Получить профессиональную оценку состояния проекта для ближайшего решения.
- Передать специалистам работу за пределами собственных знаний.
- Понимать основания и последствия решений без самостоятельного изучения всех
  подробностей проверки.

## Предусловия

1. Игорь работает с проектом через подключённый `ai-dev-team`.
2. Агенту доступны проектные материалы и правила в пределах выданных прав.

## Гарантии при успехе

1. Проверка соответствует выбранной задаче и особенностям проекта.
2. Игорь получает понятный вывод, существенные находки, основания и ограничения
   охвата, позволяющие принять ближайшее решение.
3. Подробные результаты доступны без необходимости читать их для понимания
   основного вывода.

## Минимальные гарантии

Продукт сообщает фактический охват и препятствия проверки. Непроверенные
свойства не получают успешной оценки. Согласованные границы работы сохраняются.

## Основной сценарий

1. **Игорь** просит проверить проект, не определяя программу проверки.
2. **Агент** кратко знакомится с контекстом и предлагает подходящие варианты:
   быструю проверку, проверку перед выпуском или всестороннюю проверку.
3. **Агент** объясняет ожидаемый результат и относительный объём работы каждого
   варианта. При достаточных основаниях рекомендует один из них.
4. **Игорь** выбирает вариант или описывает желаемый результат своими словами.
5. **Агент** определяет охват и применимые профильные проверки. Он уточняет
   только сведения, от которых зависит ближайшее действие.
6. **Агент** выполняет проверку, используя достаточные актуальные свидетельства
   повторно. Существенные решения передаёт Игорю с объяснением последствий.
7. **Агент** сообщает основной вывод, существенные находки, ограничения и
   следующий шаг, если он нужен. По запросу раскрывает подробности.

## Расширения

- 1а. **Игорь** уже назвал цель, охват или подходящий вариант проверки.
  **Агент** использует их без повторного меню. Существенная неоднозначность
  уточняется перед зависящим действием.
- 2а. Проекту подходит специализированная программа проверки.
  **Агент** включает её в краткий выбор с объяснением результата. Проектные
  особенности не превращаются в обязательные варианты для других проектов.
- 2б. **Игорь** поручил выпуск версии.
  **Агент** предлагает проверку перед выпуском по [ФТ-71][release], если
  предложение не отключено. Повторный общий выбор
  программы не требуется.
- 5а. Выбрана всесторонняя проверка.
  **Агент** применяет договор [полной проверки проекта][full], сохраняя
  его охват, согласования и условия завершения.
- 6а. Обязательную проверку выполнить невозможно.
  **Агент** сохраняет выполненное, называет непроверенное свойство и
  препятствие.
  Ограниченный результат не выдаётся за полное завершение.
- 6б. Найдено требующее исправления несоответствие.
  **Агент** показывает основание и предлагаемое действие. Запрос проверки сам по
  себе не разрешает изменения. Ранее выданные полномочия сохраняются.

## Основание и границы

- Сценарий принят пользователем после обсуждения общего входа «Проверь проект».
- [Цели Игоря](../personas/igor.md#цели) служат проектировочным основанием.
  Удобство для большинства пользователей не подтверждено полевым исследованием.
- Выбор программы и выполнение проверки — средства достижения цели.
  Публикация версии — отдельная задача.
