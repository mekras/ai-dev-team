# Разработка продукта

## Установка и обновление зависимостей

```shell
apm install --frozen
```

Команда APM использует внутреннюю цель `agent-skills` и клиентские цели
`claude` и `codex` из `apm.yml`, а также устанавливает точные версии из
`apm.lock.yaml`.

Чтобы обновить зависимости APM в пределах ограничений `apm.yml` и записать
результат в `apm.lock.yaml`, выполните:

```shell
apm update
```

## Самоприменение продукта

При разработке проект использует собственные переносимые роли и навыки. Их
источник находится в `.apm/`, а `apm install --frozen` разворачивает рабочие
проекции для поддерживаемых клиентов:

- навыки — в игнорируемые `.agents/skills/` и `.claude/skills/`,
- роли Claude — в `.claude/agents/`,
- роли Codex — в отслеживаемые `.codex/agents/`.

Изменяйте продуктовый примитив в `.apm/`, затем переустанавливайте пакет. Не
правьте сгенерированную копию вместо источника: следующая установка перезапишет
такую правку. После установки выполните:

```shell
apm run tests
apm audit --ci
```

Первая команда сверяет исходные навыки и роли с рабочими проекциями, компилирует
пакет для Claude и Codex и проверяет упаковку. Вторая воспроизводит установку из
файла блокировки и отклоняет дрейф.

Локальные роли маршрутизации моделей `mini_mechanical`, `luna_patch_worker`,
`spark_evidence` и `strong_reviewer`, а также `.codex/config.toml` обслуживают
разработку этого репозитория. Они не входят в переносимое ядро `.apm/`.

Локальная политика классов исполнения задаётся в игнорируемом
`.ai-dev-team/local/subagents.toml`. Переносимый запускатель поставляет
`ai-agent-supervisor`: вызывайте
`.agents/skills/ai-setup-subagents/scripts/run-execution-class` напрямую или
скопируйте его и адаптеры в `tools/` установщиками навыка. Запускатель сохраняет
назначенную и фактическую модели в локальном журнале и отклоняет расхождение.

## Проверка механики полного прохода

Классификация участия должна охватывать каждую собственную роль, навык и
инструкцию:

```shell
python3 tools/validate-project-review-capabilities.py
```

Инвентаризацию активных возможностей текущего проекта можно проверить отдельно:

```shell
python3 \
  .apm/skills/ait-project-revalidation/scripts/project_review.py \
  inventory --repo .
```

Скрипт объединяет проекции одного компонента для разных клиентов, отличает ядро,
зависимости и дополнения проекта и оставляет внешний компонент без достаточного
описания в состоянии `unknown`.

Переходы состояния, область Git, внешние изменения и конечные барьеры проверяет
узкий набор:

```shell
python3 -m unittest \
  tools/test_project_review.py \
  tools/test_validate_project_review_capabilities.py
```

## Средства корпуса знаний

Производные указатели корпуса выводятся из `data/*/items.yml` и не ведутся как
самостоятельный источник. Пересобирает их переносимое средство корпуса
`kc-pipeline`. Проверить расхождение, не меняя рабочее дерево:

```shell
python3 tools/check-knowledge-index.py
```

Эта проверка входит в `apm run tests`. Пересборка выполняется тем же скриптом с
`--write` и пишет только в `knowledge/index`.

Средство корпуса записывает пути относительно текущего каталога, поэтому
вызывать его нужно с рабочим каталогом в корне корпуса:

```shell
cd knowledge && python3 \
  ../.agents/skills/kc-pipeline/scripts/run-corpus-operations.py \
  . --rebuild-indexes
```

Запуск из корня репозитория запишет пути в виде `knowledge/data/...` и нарушит
сверку в `validate-corpus-layout.py`, который ожидает пути относительно корня
корпуса. Скрипт проверки задаёт рабочий каталог сам.

Валидатор раскладки сверяет с данными только указатель единиц. Расхождение
`index/statements.yml` он не обнаруживает — эту проверку закрывает
`tools/check-knowledge-index.py`.

Доступность публичных адресов источников проверяется отдельно, потому что
требует сети:

```shell
python3 tools/check-knowledge-sources.py
```

Скрипт не меняет корпус и складывает отчёт о запуске в
`.ai-dev-team/local/reports/corpus-source-check.md` вне Git. Ответ `403` от защиты сайта от
роботов он отделяет от настоящей недоступности.

После изменения навыка, классификации или маршрутизации выполните полную
проверку коллекции:

```shell
apm install --frozen
apm audit --ci
apm run tests
```

Управляемый многоходовой сценарий дополнительно требует наблюдаемого испытания
контроллера клиента. После первых двух ходов цель должна оставаться активной, а
третий ход должен возникнуть без новой команды человека. Ручное возобновление
сессии не заменяет это доказательство.

В Codex испытание Krosna от 2026-07-27 прошло: активная цель автоматически
создала второй и третий ходы, а счётчик изменился от `1` к `3`. Это
доказательство относится только к текущему клиенту Codex. Для другого клиента
без такого испытания проверяйте только ручной возобновляемый режим.

## Проверка графа влияния

Семантическую полноту общего договора и покрытие файлов проекта проверяют
команды:

```shell
python3 \
  .apm/skills/ait-impact-analysis/scripts/impact_graph.py \
  validate --graph .ai-dev-team/project-impact.json
python3 \
  .apm/skills/ait-impact-analysis/scripts/impact_graph.py \
  coverage --graph .ai-dev-team/project-impact.json --repo .
```

Для схемы 1 `validate` завершается с ошибкой и сообщает семантическую
неполноту. Такая схема доступна только для трассировки во время миграции.

Полный транзитивный обход, циклы, аспекты и барьер завершённости покрывает
постоянный набор:

```shell
python3 -m unittest tools/test_impact_graph.py
```

## Периодическая проверка полного пути

`apm run tests` остаётся обязательной проверкой продукта без модели и сети.
Когда изменение может повлиять на полный путь или нужен периодический срез,
используйте:

```shell
apm run product-evals
```

При первом запуске команда создаст `.ai-dev-team/local/product-evals.yml` из образца. Укажите
в локальном файле клиент, его адаптер и модель, затем повторите запуск. Средство
выполнит три сценария с известными проблемами в требованиях, решениях и
реализации. Каждый сценарий выполняется без продукта, с текущим рабочим деревом
и с предыдущим принятым выпуском. Артефакты попадут в игнорируемый каталог
`.ai-dev-team/local/product-evals/`.

Это фиксированный проверочный набор, а не представительная выборка реальных
проектов. Он показывает, какие известные проблемы обнаружила каждая версия и на
какой стадии. Набор помогает обнаружить ухудшение полного пути, но не
подтверждает снижение повторной работы, риска или стоимости. Успешная серия
получает статус `fixed_scenario_benchmark_passed` только после смысловой
проверки.

Серия начинается с трёх повторений. При превышении допустимого диапазона
пропусков средство выполняет ещё два повтора в тех же условиях. Время и токены
учитываются отдельно и не компенсируют критические нарушения или ухудшение
качества.

Статистика реального применения по версиям пока не собирается. Это отдельное
улучшение из `BACKLOG.md`, для которого сначала нужно принять требования к
данным, согласию пользователя и приватности.

Сценарии хранятся в `evals/product-scenarios.yml`. Их схему и детерминированный
подсчёт показателей можно проверить без модельного вызова:

```shell
python3 tools/run-product-evals.py --validate
python3 -m unittest tools/test_product_evals.py
```

Если правила подсчёта изменились, сохранённый запуск можно пересчитать без
повторного вызова модели:

```shell
python3 tools/run-product-evals.py --rescore .ai-dev-team/local/product-evals/<запуск>
```

## Проверка доступности знаний

`apm run tests` проверяет структуру открытого набора
`knowledge-evaluation.yml`, существование опорных фрагментов и их хэши. Эта
детерминированная проверка не вызывает модель и не измеряет качество поиска.

Для базового модельного прогона скопируйте локальную настройку:

```shell
cp .ai-dev-team/local/knowledge-evaluation.yml.sample \
  .ai-dev-team/local/knowledge-evaluation.yml
```

Проверьте допустимость передачи корпуса и опорных фрагментов выбранным моделям,
затем задайте оба разрешения в локальном файле. Настройка и результаты исключены
из Git. Запустите проверку:

```shell
mkdir -p .ai-dev-team/local/knowledge-evaluation
python3 \
  .agents/skills/kc-retrieval-evaluation/scripts/run-evaluation-suite.py \
  knowledge-evaluation.yml \
  --config .ai-dev-team/local/knowledge-evaluation.yml \
  --corpus-root knowledge \
  --output .ai-dev-team/local/knowledge-evaluation/baseline.local.json \
  --force
```

Отчёт раздельно показывает представленность целевого смысла в утверждениях,
корректность и обоснованность ответа через корпус, самоотчёт об основании и
результат без корпуса. Открытая выборка мала и пригодна для регрессии, но не
представляет весь корпус и не подтверждает полный эффект продукта.

## Выпуск версии

Перед тегом новой версии обновите `CHANGELOG.md`:

1. Оставьте только изменения, которые важны пользователю или сопровождающему:
   изменение поведения или пользовательской характеристики, публичного
   контракта, исправление заметного дефекта, самостоятельную возможность и
   смену версии зависимости, поставляемой с продуктом или зафиксированной для
   его установки.
2. Пользовательскую характеристику описывайте наблюдаемым результатом, а не
   внутренней реализацией. Для зависимости указывайте имя и прежнюю и новую
   версии. Важные последствия обновления приводите только по проверяемым
   сведениям поставщика.
3. Для небольших изменений документации пишите кратко по новому ориентиру для
   читателя, не расписывайте переносы, сокращения и перестановки текста, если
   они не дают отдельного последствия для потребителя.
4. Перенесите записи из раздела «Невыпущено» в раздел новой версии с датой.
5. Если выпуск требует действий от проектов-потребителей (переименование или
   удаление навыка, агента или правила, изменение структуры проекта или
   корпуса), добавьте в раздел версии подраздел «Действия при обновлении» с
   привязкой к примитиву. Если действий не требуется, подраздел не добавляйте.

Раздел «Действия при обновлении» читает ветка обновления версии навыка
`ait-setup` в проекте-потребителе: по нему агент проводит человека по пересмотру
проекта при переходе на новую версию продукта.

Журнал изменений самого продукта `ai-dev-team` и журналы изменений
проектов-потребителей — разные поверхности. Продуктовый `CHANGELOG.md`
обновляется в этом репозитории перед выпуском версии. Журнал целевого проекта
сопровождается через `ait-changelog` и меняется только по правилам самого
проекта.
