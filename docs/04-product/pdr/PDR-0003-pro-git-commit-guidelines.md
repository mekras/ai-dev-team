# PDR-0003: Поддержка рекомендаций Pro Git

- Статус: Принято
- Дата: 2026-07-21
- Владелец решения: владелец продукта

## Контекст

[ФТ-17](../../05-requirements/functional/ft-17.md) требует поддерживать
несколько схем
сообщений коммитов, но не закрепляет их конкретный набор. Эта запись описывает
свойства рекомендаций Pro Git с формой заголовка, адаптированной к языку
проекта, существенные для решения о включении схемы в продукт. Для русского
языка заголовок описывает завершённый результат кратким страдательным причастием
с согласованием по роду и числу; исходное повелительное наклонение сохраняется
для английского языка.

## Достоинства

1. Схема не вводит перечень типов или словарь знаков. Участнику не нужно
   дополнительно изучать классификатор изменений, а продукту — настраивать и
   сопровождать такой классификатор. Это сокращает разовые затраты на внедрение
   и постоянные затраты на сопровождение (`PGIT-001`, `PGIT-002`).
2. Русская форма совпадает с действующим правилом сообщений коммитов. Участнику
   не нужно переключаться между двумя правилами, а продукту — разрешать
   противоречие при каждой подготовке сообщения. Это снижает риск неоднородной
   истории и постоянную стоимость проверки русских заголовков.
3. Тело предлагает сохранять причину изменения и отличие от прежнего поведения
   рядом с самим изменением. Если автор заполняет тело, будущему участнику реже
   приходится восстанавливать эти сведения по коду и задачам (`PGIT-001`).
4. Git предоставляет шаблон сообщения и точку проверки `commit-msg`. Продукт
   может напоминать о структуре и проверять механические признаки через уже
   предусмотренные Git способы интеграции. Это сокращает разовые затраты на
   подключение подсказок и проверок (`GITD-001`, `GITD-002`).

## Недостатки

1. Заголовок не содержит стандартного типа изменения. Средству выпуска или
   построения журнала приходится классифицировать изменения по другому источнику
   либо применять правила конкретного проекта. Это ограничивает автоматизацию и
   увеличивает её стоимость по сравнению со схемой с машинным типом.
2. Git предоставляет точки интеграции, но не готовую проверку рекомендаций Pro
   Git. Если проекту нужен автоматический контроль, ему придётся реализовать,
   распространить и сопровождать собственный `commit-msg`; кроме того, автор
   может обойти его через `--no-verify` (`GITD-002`).
3. Ограничения длины и форма заголовка заданы как рекомендации, а не как
   однозначный машинный синтаксис. Строгая проверка может отклонять уместные
   отклонения, а мягкая — пропускать сообщения, которые расходятся с выбранным
   стилем (`PGIT-001`, `PGIT-002`).
4. Проверка длины и структуры не определяет, объяснил ли автор изменение
   достаточно точно. Чтобы история оставалась полезной, проекту всё равно нужна
   содержательная проверка сообщений, а это постоянные затраты участников.
5. Языковая адаптация отличается от англоязычных примеров Pro Git. Продукту
   нужно сопровождать отдельные примеры и проверки для каждого поддерживаемого
   языка; иначе агент может буквально перенести английскую форму в русский
   заголовок.
6. В корпусе нет сопоставимых данных о доле проектов, применяющих эти
   рекомендации, и подтверждений готовой специализированной экосистемы для них.
   Поэтому нельзя заранее рассчитывать, что распространённость снизит затраты на
   обучение или даст продукту готовые средства интеграции.

## Решение

Включить рекомендации Pro Git с формой заголовка, адаптированной к языку
проекта, в набор схем сообщений коммитов, поддерживаемых продуктом.

## Последствия

- При настройке проекта продукт предлагает рекомендации Pro Git как один из
  вариантов и применяет их после выбора.
- Для русского языка заголовок описывает завершённый результат кратким
  страдательным причастием с согласованием по роду и числу. Для английского
  языка используется повелительное наклонение.
- Ориентиры длины и поясняющее тело остаются рекомендациями читаемости, а не
  машинным синтаксисом. Содержательную точность сообщения нельзя обеспечить
  только формальной проверкой.
- Решение не назначает рекомендации Pro Git схемой по умолчанию.

## Условие пересмотра

Решение пересматривается, если языковая адаптация требует отдельных реализаций
для основных языков, автоматическая классификация сообщений становится
обязательной для целевых проектов или затраты на обучение и содержательную
проверку превышают пользу от человекочитаемой истории.

## Проверка и принятие

- Способ принятия: ручное решение владельца после независимой проверки записи.
- Независимый проверяющий: `strong_reviewer` на `gpt-5.6-sol`, отдельный процесс
  без записи, не участвовавший в подготовке текста.
- Аналитический разбор: роль `analyst`, навык `ait-analysis`; выводы отделены от
  свойств источника и привязаны к последствиям для рабочего процесса.
- Замечание независимой проверки: раздел решения оставлен пустым.
- Результат перепроверки: удалено неподтверждённое достоинство об обратимости;
  встроенные средства Git отделены от готовой проверки рекомендаций, а
  распространённость — от доказанного снижения порога входа.
- До принятия записи владелец выбрал русскую форму: заголовок описывает
  завершённый результат кратким страдательным причастием с согласованием по роду
  и числу.
- Решение принял владелец продукта 2026-07-21.
