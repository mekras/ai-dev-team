# PDR-0001: Поддержка Conventional Commits

- Статус: Принято
- Дата: 2026-07-21
- Владелец решения: владелец продукта

## Контекст

[ФТ-17](../../05-requirements/functional/ft-17.md) требует поддерживать
несколько схем
сообщений коммитов, но не закрепляет их конкретный набор. Эта запись описывает
свойства Conventional Commits, существенные для решения о включении схемы в
продукт.

## Достоинства

1. Применение Conventional Commits в разных проектах позволяет участникам
   переносить уже полученный опыт и тем самым сокращает время на освоение
   правил. Готовые средства проверки и подготовки сообщений, выпуска версий,
   ведения журнала изменений и интеграции сокращают разовые затраты на внедрение
   и последующие затраты на сопровождение (`CCMT-004`, `CCMT-005`).
2. Обязательный тип даёт средствам выпуска устойчивый машинный признак. Проект
   может использовать историю коммитов для автоматизации выпуска вместо
   повторной ручной классификации изменений (`CCMT-001`, `CCMT-003`).
3. `feat`, `fix` и обозначение несовместимого изменения передают влияние
   изменения на выпуск в самом сообщении. Автор, проверяющий и средство выпуска
   опираются на один признак вместо отдельной ручной классификации (`CCMT-002`).
4. Необязательные область, тело и служебные строки позволяют сохранить единый
   заголовок как для небольшого изменения, так и для коммита, которому нужны
   пояснение причины или дополнительные сведения (`CCMT-001`).

## Недостатки

1. Автор или агент должен классифицировать каждый коммит. Для проекта без
   автоматизации это постоянное действие не даёт соответствующей машинной пользы
   и только увеличивает стоимость рабочего процесса.
2. Ошибка в типе перестаёт быть косметической: средство выпуска или построения
   журнала изменений может неверно определить значение коммита. Поэтому продукту
   недостаточно проверить форму сообщения — нужно проверять обоснованность типа.
3. Спецификация закрепляет смысл `feat` и `fix`, но не закрывает перечень
   остальных типов. Поэтому продукт не может проверять все проекты по одному
   универсальному полному списку типов.
4. Примеры применения не показывают долю Conventional Commits среди всех
   проектов. Нельзя заранее считать, что участники уже знакомы со схемой,
   экономию времени на обучении нужно подтверждать для каждого проекта
   (`CCMT-005`).

## Решение

Включить Conventional Commits в набор схем сообщений коммитов, поддерживаемых
продуктом.

## Последствия

- При настройке проекта продукт предлагает Conventional Commits как один из
  вариантов и применяет его правила после выбора.
- Поддержка схемы включает проверку типа, области, описания, признака
  несовместимого изменения, тела и служебных строк.
- Решение не назначает Conventional Commits схемой по умолчанию и не определяет
  включение других схем в продукт.

## Условие пересмотра

Решение пересматривается, если новая версия спецификации несовместимо меняет
формат, сопровождение схемы требует отдельной реализации для основных сред или
данные целевых проектов показывают, что затраты на обучение и проверку превышают
пользу от унификации и автоматизации.

## Проверка и принятие

- Способ принятия: ручное решение владельца после независимой проверки записи.
- Независимый проверяющий: `strong_reviewer` на `gpt-5.6-sol`, отдельный процесс
  без записи, не участвовавший в подготовке текста.
- Аналитический разбор: роль `analyst`, навык `ait-analysis`, выводы отделены от
  свойств источника и привязаны к последствиям для рабочего процесса.
- Замечания независимой проверки: раздел решения оставлен пустым, из недостатка
  открытого перечня типов удалены варианты реализации.
- Повторная проверка: сведения о распространённости и средствах приняты без
  замечаний, примеры применения не выданы за измерение доли рынка.
- Решение принял владелец продукта 2026-07-21.
