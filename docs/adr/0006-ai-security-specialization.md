# ADR-0006: Специализация ИБ для использования и разработки ИИ

- Статус: Принято
- Дата: 2026-07-18

## Контекст

Целевому проекту нужен специалист по информационной безопасности ИИ, который
строит модель угроз использования внешних ИИ-сервисов и разработки ИИ-систем,
выводит из неё правила безопасной работы и проверяет соблюдение этих правил.

Общие навыки ИБ уже умеют моделировать угрозы и проводить аудит, но не задают
полный состав активов ИИ, границы между корпоративными и проектными правилами и
два разных класса результатов аудита. Без этого модель легко пропускает
контекст, инструкции, данные обучения и оценки, поиск по базе знаний, средства
агента, журналы, секреты, поставщиков и цепочку поставки.

В корпус добавлены только карточки внешних источников. Основные ориентиры: NIST,
MITRE ATLAS, OWASP, государственные рекомендации, CSA, ENISA и ISO; Yandex
Cloud, Microsoft и Сбер учтены как дополнительные источники. Полные тексты,
условия и актуальные редакции проверяются точечно перед использованием.

## Рассмотренные варианты

### Вариант 1 — отдельная роль специалиста ИБ ИИ

1. Преимущество: назначение видно без дополнительной маршрутизации.
2. Недостатки: дублируются границы, входные данные и ответственность уже
   существующего специалиста по ИБ; сопровождение двух ролей создаёт риск
   расхождения требований и проверок.

### Вариант 2 — дополнить только общие навыки ИБ

1. Преимущество: разовая стоимость мала, новых файлов почти нет.
2. Недостатки: путь от модели угроз к двум видам правил и аудиту остаётся
   неявным; маршрутизация и критерии результатов будут повторяться в задачах.

### Вариант 3 — расширить роль и добавить сквозной навык ИБ ИИ

1. Преимущество: сохраняется единая ответственность роли, а специальный путь
   явно координирует модель угроз, правила и аудит.
2. Недостаток: нужно сопровождать ещё один навык и его проверки.

## Решение

Выбран вариант 3. Роль `security-engineer` получает назначение специалиста по ИБ
ИИ. Новый навык `ait-sec-ai` координирует работу с существующими
`ait-sec-threat-modeling` и `ait-sec-audit`.

Навык охватывает внешние ИИ-сервисы, агентов и разработку ИИ-систем. В первой
версии не охватываются применение ИИ злоумышленником и ИИ для киберзащиты.

Корпоративные и проектные правила ведутся как самостоятельные документы без
общих идентификаторов контролей. Корпоративные правила задают минимум; проект
может их усилить. Ослабление допускается только по утверждённому корпоративному
исключению с владельцем, областью, сроком действия и пересмотром.

Аудит выдаёт два раздельных слоя: несоответствия принятым правилам и
рекомендованные пробелы относительно внешних ориентиров. Отсутствие
свидетельства остаётся непроверенным состоянием, а не подтверждением меры.
Правовые выводы и применимость норм передаются роли `legal`.

## Последствия

- Появляются требования, маршрут роли и проверяемый навык для моделей угроз,
  правил и аудита ИИ.
- Корпус хранит ссылки, происхождение и ограничения источников без их массового
  копирования.
- Целевой проект должен утвердить собственные корпоративные и проектные правила,
  прежде чем аудит сможет назвать нарушение.
- Владелец риска сохраняет обязанность принять остаточный риск и исключения.

## Проверка

- Проверки срабатывания отличают ИБ ИИ от общего аудита, правовой оценки и
  обычной модели угроз.
- Проверка результата требует полный состав активов ИИ, раздельные правила, два
  слоя аудита и состояние непроверенных свидетельств.
- Карточки источников проходят проверку корпуса.
- Полная проверка коллекции `apm run tests` проходит.

Условие пересмотра: если в целевых проектах потребуется отдельная постоянная
владельческая роль с полномочиями вне общей ИБ, решение пересматривается по
данным маршрутизации и аудитов.
