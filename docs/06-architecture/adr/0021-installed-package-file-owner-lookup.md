# ADR-0021: проверка владельца изменяемых файлов

## Статус

Принято.

## Контекст

[ФТ-3](../../05-requirements/functional/ft-3.md) запрещает агенту менять в
целевом проекте файл, развёрнутый пакетом APM. Действующее правило требует
перед каждой задачей с правкой прочитать в `apm.lock.yaml` списки
`dependencies[].deployed_files` всех зависимостей. В целевом проекте с пятью
зависимостями файл занимал 1 094 434 байта и содержал 1 841 путь развёртки
вперемешку с хешами содержимого. Такое чтение расходует много контекста перед
каждой правкой и подталкивает агента пропустить проверку.

ФТ-3 теперь требует, чтобы объём читаемых при проверке сведений рос с числом
изменяемых путей и не зависел от размера `apm.lock.yaml`. Защита развёрнутых
файлов при этом сохраняется.

Выбор ограничивают два обстоятельства:

- `apm find` принимает один путь за вызов. Один вызов в том же проекте занимал
  около 1,2 с.
- В августе 2026 года правило с запуском `apm find` перед изменением любого
  файла отклонили: оно могло породить тысячи лишних запусков APM.

## Факторы решения

Порядок из `AGENTS.md`: срок, риск пропуска защищённого файла, стоимость во
времени, сопровождение, обратимость, влияние на рабочий процесс.

## Рассмотренные варианты

### Вариант 1 — читать списки развёртки перед задачей

Достоинства:

1. Уже действует, не требует изменений.
2. Не запускает APM: стоимость проверки не растёт с числом путей.

Недостатки:

1. Высокий риск пропуска: тяжёлое чтение перед каждой правкой агент склонен
   пропускать.
2. Стоимость растёт с размером `apm.lock.yaml`, то есть с числом зависимостей,
   и противоречит ФТ-3.
3. Не охватывает файлы, развёрнутые из собственного пакета проекта.

### Вариант 2 — `apm find` для каждого изменяемого пути

Достоинства:

1. Опирается на описанный договор команды APM: код 0 — путь развёрнут, 1 — не
   отслеживается, 2 — блокировка отсутствует или повреждена. Формат
   `apm.lock.yaml` агенту знать не нужно.
2. Ничего не требует сопровождать на стороне продукта.
3. На каждый путь агент читает только строки с его владельцами.

Недостатки:

1. Массовая правка становится медленной: 500 путей — около 10 минут. Это
   повторяет отклонённое в августе правило и снова подталкивает к пропуску.
2. На абсолютный путь команда отвечает «не отслеживается», даже если файл
   развёрнут. Правило должно отдельно требовать путь от корня проекта.

### Вариант 3 — собственный инструмент пакетной проверки

Скрипт продукта принимает список путей и выводит владельцев по
`apm.lock.yaml`.

Достоинства:

1. Один запуск на любое число путей, поиск по 1 МБ занимает доли секунды.
2. Поведение одинаково для всех агентов и проверяется тестами.

Недостатки:

1. Самый долгий срок: разработка скрипта, тестов и поставки для обеих
   оснасток.
2. Постоянное сопровождение разбора внутреннего формата `apm.lock.yaml`. APM
   уже готовит его новую версию: в журнале изменений APM 0.35.0 договор
   lock-v3 назван неутверждённым.
3. Дублирует обратный индекс, который APM уже предоставляет через `apm find`.

### Вариант 4 — `apm find` до 20 путей, один поиск для большего числа

Достоинства:

1. Короткий срок: меняется текст правила, требование и проверка валидатора.
2. Обычная задача опирается на договор `apm find`. Проверка до 20 путей
   занимает не больше 25 с.
3. Массовая правка проверяется одним проходом по спискам развёртки. Агент
   читает только строки по своим путям. В проекте из контекста поиск занял
   около 0,01 с.
4. Откладывает собственный инструмент до появления свидетельств, что он нужен.

Недостатки:

1. В правиле две ветки, оно длиннее.
2. Ветка массовой правки зависит от формата `apm.lock.yaml`, а команду поиска
   агент составляет сам. Ошибка в ней может пропустить защищённый путь.

## Решение

Принят вариант 4. Агент проверяет каждый файл, который задача создаёт, меняет,
удаляет, переименовывает или форматирует. При переименовании проверяются старый
и новый пути. Операция над каталогом или по маске сначала раскрывается в список
файлов. Путь задаётся от корня проекта, сам `apm.lock.yaml` в контекст агента
не попадает.

- До 20 путей: `apm find <путь>` для каждого.
- Больше 20 путей: одна команда просматривает `apm.lock.yaml` и выводит для
  каждого входного пути владельцев либо отметку, что путь не найден. Пути
  сравниваются точно. Путь из `dependencies[].deployed_files` развёрнут этой
  зависимостью, путь из `local_deployed_files` — собственным пакетом проекта.
  Неизвестная версия файла блокировки или неполная классификация означают,
  что проверка не выполнена.

Если проверка не выполнена, агент не меняет путь, пока проверка не пройдёт или
человек не подтвердит, что путь не развёрнут пакетом. Развёрнутый путь, в том
числе из собственного пакета проекта, остаётся защищён без исключений. Порог
20 путей ограничивает ветку `apm find` примерно 25 секундами.

## Последствия

Разовые затраты: правка правила, требования, проверки валидатора и журнала
изменений. Будущие затраты сопровождения: сверять ветку массовой правки с
форматом `apm.lock.yaml` при обновлении APM.

Риск переделки невелик: правило текстовое и меняется обычной правкой. При
смене формата блокировки переписывается только описание ветки массовой
правки.

Собственный инструмент откладывается. Причина отсрочки: неизвестно, как часто
агенты делают массовые правки и ошибаются в поиске. Сохранение варианта ничего
не стоит: вариант 3 можно добавить позже без изменения ветки `apm find`.
Ближайшая проверка — первая массовая правка больше 20 путей в
проекте-потребителе: результат поиска сверяется с `apm find` по тем же путям.
Вариант закрывается или реализуется по условиям пересмотра ниже.

Если проект запускает `apm audit --ci`, защищённый путь, пропущенный ошибочным
поиском, будет замечен: аудит обнаруживает расхождение развёрнутого файла с
записанным хешем. Без такого запуска страховки нет.

## Проверка

Поведение агента проверяется на случаях:

- 20 путей проверяются через `apm find`, 21 путь — одним поиском,
- коды `apm find` 0, 1 и любой другой,
- несколько владельцев и владелец `.`,
- переименование файла и каталога,
- удаление или форматирование каталога с развёрнутым файлом внутри,
- неизвестная версия или повреждённая структура `apm.lock.yaml` в массовой
  ветке,
- массовый поиск, в котором часть путей не найдена.

`apm run tests` проверяет наличие обеих веток и условий остановки в правиле.
Наличие текста не подтверждает поведение, поэтому эти случаи нужны и в
сценариях оценки навыка, где находится правило.

## Условие пересмотра

Пересмотреть решение, если:

- в APM появится проверка нескольких путей за один вызов `apm find`,
- `lockfile_version` изменится и ветка массовой правки перестанет
  соответствовать формату,
- агент пропустит защищённый путь из-за ошибки в поиске,
- в сессиях проектов-потребителей агент пропускает проверку до 20 путей.
