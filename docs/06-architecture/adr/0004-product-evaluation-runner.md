# ADR-0004: Локальное средство сквозной сравнительной оценки продукта

- Статус: Заменено
- Дата: 2026-07-13
- Заменено решением: [ADR-0013](0013-product-evidence-levels.md)

## Контекст

Требования `ФТ-1` и `БТ-2` требуют проверить полный путь от свободного запроса
до передачи результата человеку, а также сравнить продукт с тем же клиентским
инструментом без `ai-dev-team` и с предыдущей принятой версией. Текущий
`apm run evals` проверяет отдельные навыки одним модельным вызовом в режиме
только чтения. Он не сохраняет диалог, не позволяет агенту изменить учебный
проект и не наблюдает решение владельца между двумя ходами.

Средство должно запускать модель отдельно от `apm run tests`, сохранять
проверяемый след и не выдавать автоматическую оценку за приёмку результата.
Локальные особенности сравнительного эксперимента не должны попадать в
переносимое ядро `.apm/`.

Факторы сравнения по правилам проекта: сроки, риски, стоимость во времени,
сопровождение, обратимость и влияние на рабочий процесс.

## Рассмотренные варианты

### Вариант 1 — расширить одноходовую оценку навыков

1. Преимущество: меньше новых файлов и команд на старте.
2. Недостаток: контракт только чтения и один ход не воспроизводят целевой
   сценарий, переделка переносимого средства смешает две разные поверхности
   проверки и повысит стоимость сопровождения для всех потребителей.

### Вариант 2 — локальное многоходовое средство запуска

1. Преимущество: изолирует изменяемые учебные проекты, решение владельца и
   сравнительные варианты, сохраняет существующий переносимый контракт навыков.
2. Недостаток: проект сопровождает отдельный запускатель и клиентские адаптеры,
   модельные прогоны требуют времени и расходуют токены.

### Вариант 3 — только ручные сравнительные прогоны

1. Преимущество: почти нет разовых затрат на оснастку.
2. Недостаток: условия и след выполнения расходятся между прогонами, поэтому
   риск ошибочного сравнения и будущая стоимость повторной работы выше.

## Решение

Выбран вариант 2: только локальное многоходовое средство одновременно
воспроизводит целевой сценарий, изолирует изменяемые проекты и сохраняет
сопоставимый след вариантов. Разовая стоимость запускателя и адаптеров ниже
будущей стоимости несопоставимых ручных прогонов, а переносимый одноходовый
контракт навыков остаётся неизменным.

В корне проекта создаётся отдельная команда `apm run product-evals`. Она
подготавливает одноразовые проекты для трёх вариантов: клиент без продукта,
текущее рабочее дерево и предыдущий принятый выпуск. Один и тот же клиент,
модель, сценарий и ответ владельца задаются локальными настройками.

Локальный пакет устанавливается с `--force` только внутри одноразового проекта:
APM иначе блокирует известные предупреждения исходного дерева и не разворачивает
вариант для сравнения. Этот флаг не применяется к рабочему проекту пользователя
и не ослабляет `apm audit --ci`.

Текущий вариант устанавливается из отдельного снимка индекса Git. Прямая
установка из корня репозитория захватывает каталог результатов и рекурсивно
вкладывает одноразовый проект в самого себя. Снимок исключает локальные
артефакты и одновременно закрепляет точный состав проверяемого изменения.

Все варианты получают одинаковую локальную инструкцию изоляции от родительского
репозитория. Варианты продукта дополнительно получают инструкцию подключения из
своего снимка, одна установка пакета без подключения не считается проверкой
целевого поведения.

Клиентские адаптеры поддерживают два действия: начало сеанса и продолжение после
решения владельца. Средство сохраняет ответы, команды, изменения файлов,
длительность и доступные показатели расхода токенов. Детерминированная оценка
проверяет пропущенные действия, неправомерные изменения до решения владельца,
готовность к приёмке и критические нарушения. Смысловая оценка остаётся за
человеком либо отдельно настроенной моделью-судьёй.

Проверочный запрос явно оставляет спорную политику за владельцем, чтобы
отсутствие остановки нельзя было объяснить делегированием выбора агенту.
Ожидаемые артефакты задаются смысловыми группами с допустимыми путями: структура
целевого проекта не должна влиять на оценку наличия требования, кода или теста.
Артефакт должен быть изменён в ходе задачи: существование исходного файла само
по себе не подтверждает выполненное действие. Маркеры решения задаются группами
синонимов. Сохранённый след можно пересчитать после исправления правил оценки
без нового вызова модели.

Возврат на доработку требует наблюдения после ручной проверки и поэтому не
выводится из двух модельных ходов автоматически.

Серия начинается с трёх повторений каждого сценария для всех трёх вариантов.
Если диапазон числа пропущенных обязательных действий текущей версии больше
двух, средство выполняет ещё два повторения всех сценариев и вариантов в той же
серии. Снимок текущей версии, предыдущая версия, модель и настройки внутри серии
не меняются. Превышение диапазона после пяти повторений означает, что эффект не
подтверждён.

Средство сохраняет распределения и рассчитывает медиану пропусков и долю
предварительно готовых результатов отдельно для каждого сценария. Текущая версия
должна превзойти вариант без продукта и не ухудшить результат предыдущей
принятой версии. Механические показатели не подтверждают эффект без завершённой
смысловой проверки всей серии человеком или настроенным оценщиком. Итоговый
вывод ограничивается проверенными сценариями.

Решение уточнено владельцем 2026-07-28 после независимой проверки. Проверка
выявила, что прежние суммы и текстовые маркеры не доказывают содержательную
готовность, отдельные запуски с разными снимками нельзя объединять, а результат
нельзя распространять за пределы проверенных сценариев. Замечания разрешены
разделением механической и смысловой проверки, фиксацией условий серии и
расчётом распределений по сценариям. После этих изменений владелец принял
правило трёх начальных и двух дополнительных повторений.

## Последствия

- `apm run tests` проверяет только схему сценариев и код подсчёта показателей,
  поэтому не вызывает модель, сеть и установку продукта.
- Фактический сравнительный прогон требует локальной модели, времени и
  отдельного решения человека по его результатам.
- Артефакты пишутся в исключённый из Git каталог `.ai-dev-team/local/product-evals/`.
- Показатели сохранённого запуска можно пересчитать командой `--rescore` без
  расхода токенов модели, исходные ответы и изменения проекта не меняются.
- Неустойчивый результат автоматически получает два дополнительных повторения
  всех вариантов. Это увеличивает время и расход токенов только для серии с
  диапазоном пропусков больше двух.
- Новые клиентские инструменты потребуют адаптера по тому же двухходовому
  контракту.

## Проверка

- Отрицательный случай с изменением файла до ответа владельца считается
  критическим нарушением.
- Текущий вариант устанавливается из снимка индекса Git, а не из рабочего корня.
- Варианты продукта содержат инструкцию подключения, а пустой вариант — только
  общую инструкцию изоляции сценария.
- Полный след с решением, артефактами, командой проверки и передачей результата
  признаётся только готовым к приёмке человеком.
- Механическая проверка не переводит серию в подтверждённый результат без
  завершённой смысловой проверки.
- Распределения, медианы, доли готовых результатов и диапазон пропусков
  рассчитываются отдельно для каждого сценария.
- `apm run tests` проходит без модельного вызова.
- Фактический запуск сохраняет отдельные результаты трёх вариантов и общую
  сводку со статусом `needs_human_decision`.

Условие пересмотра: средство пересматривается, если APM предоставит устойчивый
многоходовой контракт полного проекта либо первые прогоны покажут, что
наблюдаемых данных недостаточно для показателей `БТ-2`.
