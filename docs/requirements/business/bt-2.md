# БТ-2

[К списку требований](../../requirements.md)

## Требование

Продукт снижает зависимость результата от разовых решений человека: обязательные
роли, проверки, точки принятия решений и правила передачи результата применяются
воспроизводимо.

Ожидаемый бизнес-эффект — меньше пропущенных обязательных действий, более раннее
обнаружение дефектов и меньше повторной работы после приёмки. Снижение стоимости
разработки является производным ожидаемым эффектом, а не гарантированным
свойством каждого подключения продукта.

Наличие правил, успешные тесты пакета и завершение отдельных задач подтверждают
работоспособность механизмов продукта, но сами по себе не доказывают снижение
риска или стоимости. Эффект продукта подтверждается только сравнительной
проверкой в одинаковых условиях.

## Основание

Концепция; корпус знаний — `CCMP-022` (недостатки ранних решений повышают
стоимость поздних исправлений), `SCSU-047` (дефект дешевле исправить в день
появления), `XEM7-001`, `XEM7-002` (отдельный слой контроля результата,
проверочные случаи, показатели и порог); решение владельца.

Источники подтверждают причинную связь между поздним обнаружением дефекта и
стоимостью исправления, а также необходимость отдельной проверки результатов ИИ.
Они не доказывают экономический эффект именно `ai-dev-team`; такой вывод требует
данных сравнительной проверки.

## Показатели эффекта

Основные показатели:

1. Количество пропущенных обязательных ролей, проверок и точек решения.
2. Количество решений, которые агент неправомерно принял за человека.
3. Доля результатов, подготовленных к приёмке с критериями и доказательствами.
4. Количество возвратов на доработку из-за пропуска, который можно было найти до
   приёмки.
5. Количество критических нарушений: опасных действий, скрытых рисков и
   пропущенных обязательных проверок.

Время выполнения и расход токенов учитываются отдельно. Их уменьшение не
компенсирует ухудшение качества или появление критического нарушения.

## Критерии подтверждения

Эффект проверяется на одном наборе репрезентативных задач при одинаковом
состоянии проекта, клиенте, модели, настройках и критериях оценки.

Проводятся два сравнения:

- продукт против того же клиентского инструмента без `ai-dev-team` — для
  проверки пользы подключения;
- новая версия продукта против предыдущей принятой версии — для проверки
  отсутствия ухудшений.

Эффект считается подтверждённым для проверенного набора, если одновременно:

- нет критических нарушений;
- пропущено меньше обязательных действий, чем без продукта;
- доля подготовленных к приёмке результатов не ниже исходного уровня;
- новая версия не ухудшает критические сценарии предыдущей принятой версии;
- улучшен хотя бы один основной показатель.

До выбора числа повторов и числовых порогов нельзя заявлять процент улучшения.
Снижение стоимости подтверждается только там, где целевой проект отдельно
измеряет время повторной работы, стоимость поздних исправлений или другие
денежные и временные последствия. Без таких данных сообщается снижение
наблюдаемых рисков, а не стоимости.

## Реализация

- Менеджер проекта маршрутизирует обязательные роли, проверки и решения
  человека.
- `ai-work-result-evaluation` задаёт проверочные случаи, показатели, порог и
  сравнение с принятой исходной версией.
- `apm run tests` проверяет работоспособность механизмов и отсутствие
  структурных ухудшений; `apm run evals` запускает необязательные модельные
  оценки. Ни одна из этих команд без сравнительного набора не доказывает
  экономический эффект.
- Команда `apm run product-evals` реализует первый сквозной сценарий и три
  сравниваемых варианта. Первые фактические запуски, выбор повторов и порогов
  остаются в бэклоге продукта.

## Проверка требования

1. Валидатор защищает разделение проверяемого механизма, ожидаемого эффекта и
   экономической гипотезы.
2. Сравнительный набор должен включать свободный запрос, междисциплинарное
   изменение, решение человека, обязательную проверку и передачу результата на
   приёмку.
3. Отрицательный контроль отклоняет вывод об экономическом эффекте только по
   наличию правил, успешным тестам пакета или одному удачному ответу агента.
4. Пока сравнительный набор и его порог не утверждены, БТ-2 остаётся целевым
   эффектом с неполным доказательством.
5. Детерминированная проверка `python3 tools/run-product-evals.py --validate`
   проверяет схему сценария без модели и сети; отдельные модульные тесты
   отклоняют изменение до решения владельца как критическое нарушение.
