# КАЧ-8. Завершаемость управляемой проверки

[К списку требований](../../requirements.md)

## Требование

Активная управляемая проверка должна воспроизводимо доходить до завершения либо
явного препятствия без дополнительных команд «продолжай» от пользователя.

Управляемый режим запускается только при наличии контроллера продолжения уровня
`/goal` или равнозначного механизма. Обычная инструкция навыка не считается
достаточной гарантией. Первоначальный запрос привязывает проверку к доступному
контроллеру без дополнительной технической команды пользователя. Если
подходящего контроллера нет, продукт сообщает об ограничении и предлагает ручной
возобновляемый режим без обещания автоматического завершения.

До и после каждого шага продукт сохраняет локальное состояние, связанное с
текущим рабочим каталогом и не добавляемое в Git. Состояние содержит как минимум
версию формата, снимок проверяемой области, инвентаризацию возможностей, текущую
область работы, найденные проблемы, решения пользователя, выполненные проверки и
следующее действие. Первый барьер хранит результат поиска концепции, корневые
инструкции с указателем, полный найденный состав концепции и применение её
первой смысловой проверки. До доказанного успешного завершения этого применения
состояние не разрешает другую предметную работу. Неуспешный результат оставляет
доступными только исправление проблем концепции и повторную проверку.

После успешной проверки концепции второй барьер хранит результат поиска корпуса
знаний, его полный доступный состав, технический допуск и отдельную смысловую
проверку. До завершения второго этапа состояние не разрешает работу в остальных
областях. Неуспешный результат допускает только исправление проблем текущей фазы
корпуса и её повторную проверку.

Выполненная проверка содержит отдельное применение возможности, версию её входа,
проверяемую поверхность, обоснование приоритета и наблюдаемое доказательство.
Для проверочной возможности доказательство также содержит фактический охват,
проверяемые выводы и предметный артефакт из области Git, отличный от контракта
возможности. Для смысловой проверки состояние дополнительно содержит заявленный
перечень предметных файлов, наблюдения по каждому файлу, диапазоны и хеши
прочитанных фрагментов, связи выводов с наблюдениями и проверку возможного
опровержения. Для полного класса документов состояние также хранит индекс или
шаблоны обнаружения, развёрнутый набор файлов, профильные критерии, требуемый
охват критериев и результат их проверки. При ожидании решения состояние
дополнительно хранит самодостаточный запрос для текущего снимка: вид полной
проверки, точное название проверяемого проекта, понятный предмет текущей
проверки, его связь с общим проходом, проблемы, последствия, предлагаемое
действие, границу изменения, способ проверки и один точный вопрос владельцу
решения по всей группе.

Процесс различает состояния:

- «выполняется»
- «ожидает решения»
- «заблокировано»
- «прервано»
- «завершено»
- «завершено с принятыми рисками»

Агент не выдаёт итоговый ответ, пока процесс находится в состоянии
«выполняется». После прерывания он восстанавливает следующий шаг из локального
состояния. Изменение входящих в область файлов вне согласованного исправления
останавливает зависимую работу до уточнения, чтобы не смешивать результаты
разных состояний репозитория.

Статус «завершено» допустим, только если все обнаруженные применимые области
получили конечный результат, все найденные проблемы исправлены или признаны
неприменимыми, все исправления проверены, а непроверенные области отсутствуют.
Статус «завершено с принятыми рисками» дополнительно допускает оставшиеся
неблокирующие проблемы только при явном решении пользователя по каждой из них.

## Проверка

1. Длительный сценарий проходит не менее трёх автоматических продолжений без
   команды пользователя и достигает конечного состояния.
2. Промежуточная сводка в состоянии «выполняется» не содержит признака
   завершения и сопровождается следующим автоматическим шагом.
3. Прерывание после сохранённого шага возобновляет работу с назначенного
   следующего действия без потери проблем и решений.
4. Отсутствие контроллера продолжения отклоняет запуск управляемого режима и не
   маскируется обычной инструкцией «работай до конца».
5. При доступном контроллере первоначальный запрос запускает управляемый режим
   без дополнительной команды пользователя.
6. Непроверенная применимая область или нерешённая блокирующая проблема не
   допускает статусы завершения.
7. Изменение проверяемого файла вне согласованной группы останавливает зависимый
   этап и показывает расхождение.
8. Самооценка `passed` без отдельного применения и наблюдаемого доказательства
   не допускает закрытие этапа или процесса.
9. Конечный переход повторно вычисляет живой снимок Git и инвентаризацию и
   отклоняется при расхождении с сохранённым состоянием.
10. Прерывание после любого применения сохраняет его обоснование приоритета,
    результат и наиболее ценное известное следующее действие.
11. Общая техническая команда без предметного артефакта, охвата и проверяемых
    выводов не закрывает проверочную возможность.
12. Перечень предметных файлов и текст выводов без наблюдений по каждому файлу,
    связей выводов с наблюдениями и отклонённого опровержения не закрывают
    смысловую проверку.
13. Ручной выбор части файлов из индексированного класса документов, отсутствие
    результата обязательного критерия или найденная смысловая проблема не
    допускают закрытие области.
14. Ожидание решения недоступно без сохранённого самодостаточного запроса,
    связанного с текущей группой проблем и живым снимком Git. Изменение снимка
    очищает запрос и прерывает процесс.
15. Первое предметное применение, не связанное с найденной концепцией,
    отклоняется независимо от его ожидаемого влияния или технической простоты.
16. Миграция состояния, созданного до появления барьера концепции, архивирует
    прежний снимок и открывает новый проход с поиска концепции. Прежние
    применения не доказывают соблюдение нового порядка.
17. Ручная запись состояния концепции как проверенного без связанного успешного
    применения и полного смыслового следа не открывает остальные области.
18. Неуспешная проверка концепции с найденной проблемой не открывает остальные
    области до исправления и повторной успешной проверки.
19. После успешной проверки концепции контроллер допускает только поиск,
    технический допуск и смысловую проверку корпуса. Остальные области
    открываются после доказанного завершения второго этапа.
