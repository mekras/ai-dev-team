# ФТ-8. Инициативное предложение записей решений

[К списку требований](../../requirements.md)

## Требование

Продукт предлагает фиксацию решений, не дожидаясь прямого запроса заказчика:

- при настройке проекта, на этапе проработки структуры документации, продукт
  предлагает завести подходящие журналы; до первой предметной записи предлагает
  договор журнала с его видом, предметной границей, статусной моделью, форматом
  идентификаторов и правилом «какое решение в какой журнал»;
- первая запись журнала фиксирует одно значимое решение соответствующего вида;
  продукт не создаёт служебную запись о ведении журнала и не помещает
  организационную политику в ADR только ради начального номера;
- при первом значимом решении, принятом заказчиком в диалоге, продукт предлагает
  завести журнал (если его нет) и записать решение;
- если в ходе работы продукт опирается на значимое решение, которого нет в
  журнале, он предлагает ретроспективную запись с явной пометкой о её характере.
- на ранней стадии подходящего SaaS или самостоятельно развёртываемого сервиса
  продукт предлагает ADR об использовании The Twelve-Factor App до архитектурных
  решений по факторам согласно [ФТ-12](ft-12.md).

Отказ заказчика фиксируется в состоянии проекта, и продукт не повторяет
предложение без нового запроса.

## Основание

[ФТ-7](ft-7.md) требует сохранять значимые решения. Без инициативного
предложения первое решение остаётся только в диалоге, если заказчик ещё не
создал журнал. Рабочий образец механики — предложение журнала изменений и
корпуса знаний при настройке.

## Связи

- Расширяет [ФТ-7](ft-7.md) точками инициативного создания записей и журналов.
- Подготавливает запись до действия по [ФТ-9](ft-9.md).
- [ФТ-12](ft-12.md) задаёт предметные условия раннего предложения ADR о The
  Twelve-Factor App.

## Реализация

- [ait-setup](../../../.apm/skills/ait-setup/SKILL.md) предлагает журналы при
  настройке и сохраняет отказ в поле `setup.decision_records` файла
  `.ai-dev-team-state.yml`.
- [ait-docs-structure-design][a] предлагает журналы при проектировании места
  решений в документации.
- [ait-decisions](../../../.apm/skills/ait-decisions/SKILL.md) предлагает журнал
  после первого значимого решения и ретроспективную запись, когда работа
  опирается на незаписанное решение.
- [ADR-0002](../../adr/0002-cross-cutting-decision-records.md) фиксирует
  реализацию общей дисциплины отдельным сквозным навыком.
- [ait-twelve-factor](../../../.apm/skills/ait-twelve-factor/SKILL.md)
  предлагает ADR после положительной оценки применимости на ранней стадии
  проекта.

## Проверка

1. Сценарии срабатывания покрывают первое принятое решение и опору на
   незаписанное решение без прямой просьбы заказчика создать запись.
2. Сценарий настройки после отказа записывает
   `setup.decision_records.status: declined` и не предлагает журналы повторно.
3. Регрессионный сценарий настройки отделяет договор журнала от первой записи и
   не объединяет изменение `AGENTS.md`, запись решения и файл состояния одним
   подтверждением.
4. `apm run tests` проверяет наличие трёх точек инициативы, поля состояния и
   постоянных сценариев отказа и создания нового журнала.
5. Сценарий подходящего SaaS предлагает ADR до решений по факторам, а сценарий
   библиотеки не предлагает его без архитектурной значимости.
