# ФТ-3. Подключение продукта через APM

[К списку требований](../README.md)

## Требование

Продукт должен подключаться к целевому проекту штатными средствами менеджера
пакетов APM как зависимость для разработки. Команда первичной установки должна
передавать параметр `--dev`, чтобы пакет попал в `devDependencies.apm` целевого
проекта.

Каждая команда первичной установки должна содержать ровно одну явную цель:
`--target claude` или `--target codex`. Значение `all`, список целей и команда
без `--target` не являются пользовательским способом подключения. Ограничение
одной команды одной целью не запрещает пользователю явно подключить другой
клиентский инструмент отдельным поддерживаемым действием.

Проверка публикуемого пакета может охватывать все поддерживаемые цели, но не
должна создавать их клиентские файлы в целевом проекте пользователя.

После подключения агент до изменения файла целевого проекта определяет,
развёрнут ли его путь пакетом APM и каким. Проверке подлежит каждый файл,
который задача создаёт, изменяет, удаляет, переименовывает или форматирует, в
том числе внутри затрагиваемого каталога. Объём сведений, которые агент читает
для проверки, растёт с числом таких путей и не зависит от размера
`apm.lock.yaml`. Если задача меняет больше 20 путей, агент проверяет их одним
поиском, а не отдельным запуском APM на каждый путь.

Развёрнутый пакетом файл агент не изменяет, не удаляет, не переименовывает и не
форматирует в целевом проекте. Он называет путь и пакет-владелец и переносит
исправление в исходный файл в репозитории этого пакета. Если владелец —
собственный пакет целевого проекта, исходный файл находится в самом проекте.
Если владельцев несколько, агент называет всех и согласует с человеком, где
исправлять исходник. Если владельца пути установить не удалось, агент не меняет
этот путь до успешной проверки или подтверждения человека, что путь не
развёрнут пакетом.

## Основание

[Концепция](../../01-concept/README.md) определяет продукт как подключаемую
команду. Запрос пользователя задаёт категорию подключения: зависимость для
разработки.
[ПТ-3. Настройка только выбранных клиентских инструментов](../user/pt-3.md)
требует не создавать файлы для инструментов, которых пользователь не выбирал.

Зависимость стоимости проверки от числа изменяемых путей задал пользователь 19
ноября 2026 года[^owner-lookup]. Прежнее правило требовало перед каждой
задачей с правкой читать в `apm.lock.yaml` списки развёрнутых файлов всех
зависимостей. В крупном целевом проекте это расходует много контекста и
подталкивает агента пропустить проверку.

Ограничение числа запусков APM сохраняет причину, по которой в августе 2026
года отклонили проверку каждого файла отдельным запуском `apm find`: такое
правило могло породить тысячи лишних запусков[^runs]. Выбор способа проверки
записан в [ADR-0021][adr-0021].

## Реализация

- Пакет объявлен в [apm.yml](../../../apm.yml) с внутренней целью
  `agent-skills` и клиентскими целями `claude` и `codex`. Внутренняя цель не
  меняет пользовательскую команду подключения.
- [README](../../../README.md) содержит команды `apm install --dev` для обеих
  целей и следующий шаг «Настрой проект».
- [ait-setup](../../../.apm/skills/ait-setup/SKILL.md) завершает настройку уже
  установленного продукта в целевом проекте.
- [Маршрутизатор][routing] задаёт защиту файлов установленных пакетов вне
  шагов полного маршрута. Поэтому она действует в любом режиме менеджера и
  доходит до агента при рукописном `AGENTS.md`. Если путей не больше 20,
  владельца каждого агент узнаёт командой `apm find`. Команда ищет путь по
  обратному индексу `apm.lock.yaml` и выводит только
  пакеты-владельцы[^apm-find]. Больше 20 путей агент проверяет одной командой:
  она просматривает списки развёрнутых файлов в `apm.lock.yaml` и выводит для
  каждого пути владельцев либо отметку, что путь не найден.

[^owner-lookup]:
    Пользователь поручил исправить правило так: «агент перед изменением файла
    узнаёт, развёрнут ли этот путь пакетом и каким. Затраты на проверку
    зависят от числа изменяемых путей, а не от размера блокировки. Защита
    развёрнутых файлов сохраняется: такой файл в целевом проекте не
    изменяется, а исправление уходит в репозиторий пакета-владельца».
    Основанием послужил замер в целевом проекте с пятью зависимостями:
    `apm.lock.yaml` занимал 1 094 434 байта и содержал 1 841 путь развёртки
    вперемешку с хешами содержимого.

[^apm-find]:
    Журнал изменений APM, выпуск 0.17.0 от 3 июня 2026 года, раздел «Added»,
    запись об `apm find`:
    <https://github.com/microsoft/apm/blob/main/CHANGELOG.md>. Неотслеживаемый
    путь завершает команду с кодом 1, отсутствующий или повреждённый файл
    блокировки — с кодом 2.

[^runs]:
    26 августа 2026 года первая версия правила требовала запускать `apm find`
    перед изменением любого файла. Пользователь отклонил её: «Это плохое
    правило, оно может породить тысячи лишних запусков apm. Надо сузить его».
    19 ноября 2026 года один запуск `apm find` в целевом проекте занимал
    около 1,2 с.
