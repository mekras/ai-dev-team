# ФТ-51. Проверка границ между агентами

[К списку требований](../README.md)

## Требование

При моделировании системы с передачей задачи, контекста или результата между
агентами продукт должен показывать для каждой передачи отправителя,
получателя, происхождение данных, порученные и фактически доступные права,
способ привязки результата к поручению и распределение действий: чтение,
изменение, проверка, разрешение и исполнение. Совмещение действий обозначается
явно. Название роли не подтверждает ограничения доступа.

Для этих границ продукт должен рассматривать подмену отправителя или
результата, расширение полномочий, перенос недоверенных инструкций,
воздействие на проверяющего и утрату ограничений при пересказе. Применимость
и результаты проверок сохраняются в покрытии модели. Конечное последствие
связывается с последовательностью обоснованных или условных переходов,
а не с суммой прав всех участников.

Неизвестные участники, права, протоколы или назначения остаются открытыми
вопросами. Проверка не должна приписывать системе MCP либо делегирование без
оснований. Если межагентных передач нет, продукт должен указать неприменимость
этой проверки, сохранив рассмотрение остальных угроз ИИ.

## Основание

Поручение владельца от 7 октября 2026 года после оценки
[AI-Threat-Modeling-Claude-Skill][origin]. Дельта `specification_change`
входит в подтверждённый объём проверки цепочек и границ между агентами.

[Концепция продукта](../../01-concept/README.md) требует воспроизводимости
работы. Книга Адама Шостака «Threat Modeling: Designing for Security» задаёт
анализ модели системы и допущений: `TMDS-007`, `TMDS-027` в корпусе.
[Исследование многоагентных угроз][paper], разделы 1.1 и 2, различает
проверку и изменение результата, рассматривает наследование полномочий и
потерю цели при делегировании. Исследовательский сценарий не подтверждает
наличие угрозы в конкретной системе.

## Реализация

[ait-sec-ai][skill] и справка о границах между агентами.

## Проверка

1. Вредоносный текст проходит через читающего агента к исполнителю, но
   читающему не приписываются ключи исполнителя.
2. Фактический доступ «проверяющего» к исполнению отмечается явно.
3. Проверка отправителя не считается проверкой правомерности действия.
4. Потеря ограничения поручения и неизвестные проверки конечного API
   отражаются отдельно с нужными свидетельствами.
5. Пассивный чат без делегирования не получает вымышленных границ агентов.
