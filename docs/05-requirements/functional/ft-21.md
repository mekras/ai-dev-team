# ФТ-21. Динамический охват полной проверки

[К списку требований](../README.md)

## Требование

В начале полной проверки и при её возобновлении продукт получает фактический
состав активных ролей, навыков и правил из трёх источников:

- переносимого ядра `ai-dev-team`
- установленных зависимостей продукта
- активных дополнений целевого проекта

Продукт классифицирует каждую найденную возможность как предметную проверку,
источник ограничений, подготовительное или исправляющее действие либо
неприменимую к проверке возможность. План строится по назначению и применимости
возможностей, а не по закрытому перечню их имён в координирующем навыке.

Для собственных ролей, навыков и правил продукта действует машиночитаемая
классификация участия в полной проверке. Структурная проверка сопоставляет её с
фактическим составом переносимого ядра и отклоняет компонент без классификации
либо классификацию без компонента.

Для возможностей зависимостей и целевого проекта продукт использует их
метаданные и инструкции. Возможность, которую нельзя однозначно
классифицировать, не пропускается молча и блокирует вывод о полном охвате.

Изменение активного состава при возобновлении проверки требует повторной
инвентаризации и обновления плана. Новая применимая проверка повторно открывает
соответствующий завершённый этап. Прежний результат используется повторно,
только если состав его проверок и проверенные входные данные не изменились.

Применение каждой возможности хранится отдельно и связано с её версией,
проверяемой поверхностью, действием и наблюдаемым результатом. Одна общая
самооценка или структурная проверка состава не подтверждает применение
нескольких предметных возможностей.

## Основание

[ПТ-7](../user/pt-7.md), [ПР-1](../rules/pr-1.md), [ПР-2](../rules/pr-2.md) и

механизм маршрутизации и проверять его на подходящих и неподходящих запросах.

## Проверка

1. Структурная проверка перечисляет фактические собственные роли, навыки и
   правила и подтверждает наличие классификации для каждого компонента.
2. Отрицательный сценарий добавляет новый собственный навык проверки без
   изменения координатора и получает отказ из-за отсутствующей классификации.
3. После добавления классификации тот же навык входит в план подходящего
   репозитория без изменения процедуры координатора.
4. Новый неприменимый навык учитывается в инвентаризации, но не создаёт ложную
   область проверки.
5. Неклассифицируемое дополнение зависимости или целевого проекта блокирует
   вывод о полном охвате и остаётся видимым пользователю.
6. Изменение состава возможностей между остановкой и возобновлением обновляет
   план, открывает затронутый этап и не сбрасывает независимые подтверждённые
   результаты без причины.
7. Попытка закрыть несколько применимых возможностей общей записью `passed` без
   отдельных применений и наблюдаемых результатов получает отказ.
