# ФТ-2. Контроль качества результата

[К списку требований](../README.md)

## Требование

До передачи результата ИИ человеку или в следующий этап продукт должен выполнить
воспроизводимый контроль качества по проверочным случаям, критериям оценки и
порогу пригодности.

Результат, который не достиг порога пригодности, продукт не должен передавать
как готовый. Частично проверенный результат можно передать только по отдельному
решению человека после сообщения о пропущенных проверках, известных ограничениях
и остаточном риске.

Контроль должен оставлять проверяемый след: применённые проверочные случаи,
критерии или метрики, порог пригодности, результаты выполненных проверок и
сведения о пропущенных проверках.

## Основание

[Концепция](../../01-concept/README.md) требует системно применять проверки
качества, сохраняя за человеком определение замысла и приёмку результата.

[БТ-1. Целостный контур агентной разработки](../business/bt-1.md) включает
контроль результата в единый путь до явной приёмки.
[БТ-2. Раннее выявление ошибок и упущений](../business/bt-2.md) требует выявлять
ошибки как можно раньше, а
[ПТ-1. Путь пользователя от подключения к приёмке](../user/pt-1.md) требует
передавать пользователю проверяемый результат со сведениями о выполненных и
пропущенных проверках.

Книга Джеффа Сазерленда «Scrum. Революционный метод управления
проектами»[^scsu-032] отделяет решение исполнителя о завершении от результата,
который проверил пользователь. Книга Хенрика Книберга «Scrum и XP. Заметки с
передовой»[^scxp-024] требует явно определять критерий готовности.

## Связи

- Уточняет контроль качества целостного контура из [ФТ-1](ft-1.md).
- Обеспечивает межэтапный контроль для
  [БТ-2. Раннее выявление ошибок и упущений](../business/bt-2.md).
- Следует после своевременного выбора проверки по
  [ФТ-26. Раннее назначение проверок](ft-26.md).
- Обеспечивает проверяемость результата перед приёмкой по
  [ПТ-1. Пути пользователя от подключения к приёмке](../user/pt-1.md).

## Реализация

- [ai-work-control](../../../.agents/skills/ai-work-control/SKILL.md) определяет
  способ проверки до начала существенной работы.
- [ai-work-result-evaluation][a] задаёт проверочные случаи, метрики, порог
  пригодности, сравнение с базовой линией и решение по результату проверки.
- [project-manager](../../../.apm/agents/project-manager.agent.md) назначает
  проверку перед публикацией или дальнейшим использованием результата.
- Файлы `evals/triggers.json` и `evals/result-scenarios.json` хранят проверочные
  случаи навыков, их структура проверяется командой `apm run tests`.
- `apm run evals` отдельно запускает необязательную модельную оценку всей
  коллекции, выбранного навыка или отдельного сценария по локальным настройкам.

## Проверка

Требование проверяется по тому, останавливает ли контроль качества передачу
непригодного результата человеку или в следующий этап.

1. `apm run tests` без модели и сети проверяет наличие и структуру проверочных
   случаев, скрытые символы, описания навыков, переносимость ссылок и
   собираемость пакета.
2. `apm run evals` с локально выбранными моделями применяет навыки к сценариям,
   оценивает результаты моделью-судьёй и сообщает проваленные случаи.
3. Для результата существенной работы прослеживаются поверхность проверки,
   случаи, метрика или критерий, порог пригодности и одно из решений: принять,
   доработать, отклонить или передать решение человеку.
4. Результат ниже порога пригодности не передаётся как готовый.
5. Передача частично проверенного результата требует отдельного решения человека
   после сообщения о пропущенных проверках, ограничениях и остаточном риске.
