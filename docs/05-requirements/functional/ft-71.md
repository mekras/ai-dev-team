# ФТ-71. Углублённая проверка при выпуске версии

[К списку требований](../README.md)

## Требование

При запросе выпустить новую версию продукт предлагает углублённую проверку, если
она явно не отключена в правилах целевого проекта. Отсутствие настройки
означает, что предложение включено. Агент кратко показывает применимый состав
работ и ожидаемый результат, затем получает решение до подготовки самого
выпуска. До решения допустимы краткое чтение состояния проекта и обязательная
входная техническая подготовка среды. Продукт не меняет версию и журнал
изменений, не запускает выпускную сборку или выпускной прогон проверок и не
создаёт коммит или тег выпуска. Сам факт отправки асинхронного вопроса не
разрешает продолжать эти действия. Молчание не считается согласием.

При согласии продукт выполняет углублённую проверку. При отказе продолжает
обычный выпуск по местному порядку. Явное отключение предложения в проекте
позволяет сразу перейти к этому порядку. Отказ и отключение не отменяют
обязательные проверки выпуска. Отказ для одной версии не меняет правила проекта.
Прямой запрос углублённой проверки уже выражает согласие на неё. Явно принятый
проектом обязательный этап выполняется по его правилам.

Решение и выполненная углублённая проверка относятся к конкретному выпуску. При
продолжении того же выпуска продукт использует их повторно, а существенные
изменения проверяет в их области. Отказ от углублённой проверки в прошлом
выпуске не отключает предложение для следующего.

Продукт устанавливает кандидат выпуска, изменения с предыдущей версии,
применимые ограничения и полномочия. Существующие проверки целевого проекта
остаются основой. Достаточные результаты для того же кандидата и условий
используются повторно, а недостающие проверки выполняются доступными средствами.

Углублённая проверка начинается с широкого обзора состояния проекта. Её область
определяется после обзора с учётом особенностей проекта и согласованной задачи,
без предварительного ограничения только рисками. Обзор охватывает
согласованность требований, реализации, документации, проверок и поставки,
устройство кода и использование ресурсов. Направления углубления выбираются по
значимости проблем и ожидаемой пользе улучшений. Риски, охват потребителей,
стоимость проверки, исправления и регрессии учитываются при расстановке
приоритетов. Приоритет полезных проверок не задаёт квоту исправлений или долю
тестов, которую разрешено пропустить.

Для выбранной проблемы или области продукт формулирует сценарий, ожидаемый
результат и способ проверки на кандидате выпуска. Сценарии учитывают тип
продукта, поддерживаемые среды, установку, обновление и существенные изменения
версии. Неприменимые сценарии не навязываются. Команды, инструменты, правила VCS
и публикации определяет целевой проект.

По каждой существенной находке продукт показывает свидетельство, последствия,
предлагаемое исправление и проверку результата. Исправления выполняются в
пределах уже полученных полномочий. Требуемое согласование конкретной группы и
расширение области обрабатываются по правилам целевого проекта. Структурные и
ресурсные улучшения обосновываются наблюдаемой проблемой и ожидаемой пользой.
Высокий риск выпуска не является условием их рассмотрения.

Итог различает выполненные проверки, устранённые дефекты, остаточные риски и
непроверенные области. Обязательная проверка без свидетельства не получает
успешный итог. Выборочный проход не подтверждает полную проверку проекта. При
остановке сохраняются основания, результаты и согласования в доступном следе,
достаточном для продолжения. Публикация выполняется только по имеющемуся
разрешению и местному порядку.

## Основание

[Концепция продукта](../../01-concept/README.md) требует соразмерного управления
сложностью. [БТ-2](../business/bt-2.md) задаёт раннее выявление ошибок.
Пользователь поручил предлагать этот этап при обычном запросе выпуска версии,
если проект явно его не отключил, затем назвал этап «углублённая проверка»,
чтобы не сужать его рамки преждевременно. Это изменение поведения продукта по
[ФТ-38](ft-38.md). Порядок предложения, согласия и отказа сохраняется.

## Реализация

Навык `ait-release` ведёт выпуск по местному порядку и предлагает углублённую
проверку. После согласия он передаёт выбранную программу в общий навык
`ait-project-check` по [ФТ-72](ft-72.md) без повторного меню. Условная справка
общего навыка сохраняет проход через профильные навыки и средства проекта.
Собственный скрипт не нужен: выбор
направлений углубления и оценка результата требуют предметного контекста, а
механические проверки уже принадлежат проекту. Навигация различает выпуск
версии, отдельную операцию VCS и полную перепроверку.

## Проверка

1. Обычный запрос выпуска, в том числе «Выпускай версию», приводит к предложению
   углублённой проверки при отсутствии явного отключения в проекте. До ответа
   дополнительный проход, подготовительные изменения и публикация не
   выполняются. Асинхронный вопрос без ответа сохраняет это ограничение.
2. Явное отключение в проекте убирает предложение, сохраняя обычный порядок и
   обязательные проверки. Отсутствие настройки не считается отключением.
3. Согласие запускает углублённую проверку, отказ позволяет продолжить обычный
   выпуск. Продолжение одной версии не запрашивает уже принятое решение
   повторно. Отказ не создаёт постоянного отключения и не переносится на новую
   версию.
4. Для библиотеки проверяются её поставка и совместимость обновления, а для
   приложения — применимые среды и изменённые пользовательские пути. APM,
   Android, Git и отдельный файл настройки не обязательны.
5. Успешные проверки повторно используются только для того же кандидата и
   условий. Существенный непроверенный риск требует предметной проверки.
6. Риск неработающего обновления получает приоритет перед косметической правкой.
   Число находок не прекращает проверку автоматически.
7. Запрет записи сохраняется. Уже разрешённое исправление не требует повторного
   согласования неизменной области.
8. Недоступная обязательная проверка остаётся непроверенной. Итог показывает
   препятствие и следующий шаг, сохраняя проверенные результаты.
9. Углублённая проверка не запускает публикацию без разрешения и не выдаёт
   выборочный проход за полный аудит.
10. Полезность оценивается по найденным существенным проблемам и обоснованным
    улучшениям сверх обычных проверок, времени и сопровождению сценариев.
    Прохождение синтетических случаев само по себе полезность не подтверждает.
11. Наблюдаемая проблема сопровождаемости может стать направлением углубления
    без доказанного существенного риска выпуска. Риск учитывается как один из
    факторов приоритета, область не ограничивается им заранее.
12. Явное отключение этого же этапа под прежним названием сохраняет смысл.
