# ФТ-7. Журналы решений

[К списку требований](../README.md)

## Требование

Продукт ведёт в целевом проекте журналы значимых проектных решений. Запись
решения (DR) сохраняет обоснование выбора, определяющего свойства и устройство
продукта либо договорённости участников проекта о целях, ответственности и
поставке результата. Запись позволяет при дальнейшем развитии проекта понимать
причины выбора, рассмотренные альтернативы и принятые последствия.

До оценки значимости продукт устанавливает область решения по концепции
целевого проекта. Внутри этой области он оценивает затронутые требования и
обязательства, последствия и условия пересмотра выбора. Потребность сохранить
сведения сама по себе не определяет область DR.

При настройке существующего проекта продукт проверяет договоры принятых
в проекте журналов по этой области. При расхождении он сам готовит правку
договора и выполняет её в пределах поручения на настройку. Изменение принятой
владельцем предметной границы требует его решения. Наличие журнала или отметки
о его настройке не заменяет эту проверку.

Набор журналов открытый: продукт предлагает типовые виды (архитектурные — ADR,
организационные — ODR, по документации — DDR), а состав и границы журналов
определяет целевой проект, новый вид решений не требует изменения продукта. Для
нового журнала проект отдельно определяет вид, предметную границу, путь и формат
имени записи. Тип записи должен быть виден в её устойчивом идентификаторе и
имени файла. Для типовых видов продукт предлагает формат `?DR-NNNN.md`:
`ADR-0001.md`, `ODR-0001.md`, `DDR-0001.md`. Существующее соглашение проекта
сохраняется до отдельного решения о миграции.

Каждая запись решения независимо от вида фиксирует минимум: контекст с
формулировкой проблемы, решение с обоснованием и последствия. Способ проверки и
условие пересмотра в обязательный минимум не входят. Их записывают, когда у
решения есть проверяемый критерий успеха или известное условие возврата к
выбору. Статусы записей ведутся по единой модели продукта:

- `Предложено` — решение оформлено и ожидает принятия,
- `Принято` — решение действует,
- `Отклонено` — предложение рассмотрено и не принято, причина отказа указана в
  записи,
- `Устарело` — принятое решение больше не рекомендуется, замена не назначена,
- `Заменено` — принятое решение заменено другим, связанным с исходной записью.

Форма записи отражает то, как решение принималось:

- полная форма применяется, когда варианты сравнивались по достоинствам и
  недостаткам. Запись содержит разбор каждого рассмотренного варианта,
- краткая форма применяется, когда варианты не рассматривались либо были
  отсеяны по правилу проекта, ограничению или другому заранее известному
  условию. Запись называет отвергнутые варианты и условие отсева, разбор
  достоинств и недостатков не требуется.

Решение, принятое агентом без участия человека, записывается в полной форме,
если проект или пользователь не установили другое.

## Основание

[БТ-1](../business/bt-1.md) (согласованный порядок принятия решений), корпус
знаний — справочник по записям решений `adr.github.io`: исходные статусы
`proposed`, `accepted`, `deprecated`, `superseded`[^adrg-011] и расширение
подхода ADR с архитектурных на любые организационные решения[^adrg-014].
Исходная модель не позволяет отличить ожидающее предложение от рассмотренного и
отклонённого, а статусы `deprecated` и `superseded` относятся только к ранее
действовавшим решениям.

Состав обязательного минимума и выбор формы записи закреплены решением владельца
продукта [ADR-0019][c]: запись должна показывать фактический ход принятия
решения, а разделы о способе проверки и условии пересмотра нужны только там, где
у решения есть проверяемый критерий успеха или известное условие возврата к
выбору.

## Реализация

- [ait-decisions](../../../.apm/skills/ait-decisions/SKILL.md) применяет единую
  модель ко всем видам журналов.
- [ait-setup](../../../.apm/skills/ait-setup/SKILL.md) проверяет и исправляет
  договоры существующих журналов при повторной настройке проекта.
- [Справочник процесса][a] определяет смысл каждого статуса и допустимые
  переходы.
- [Каталог шаблонов][b] требует указывать статус по единому перечню.
- [Слой понятий](../../../knowledge/concepts.yml) отделяет четыре статуса из
  справочника `adr.github.io` от проектного расширения `Отклонено`.
- [ADR-0003](../../06-architecture/adr/0003-rejected-decision-status.md)
  фиксирует выбор
  отдельного статуса для рассмотренного и не принятого предложения.
- [ADR-0019](../../06-architecture/adr/0019-decision-record-form-by-process.md)
  фиксирует выбор формы записи по ходу принятия решения.

## Проверка

1. В целевом проекте запись любого вида создаётся по одной дисциплине, для
   записи прослеживаются обязательные секции.
2. Предложение, которое рассмотрели и не приняли, получает статус `Отклонено` и
   сохраняет причину отказа, оно не остаётся `Предложено` и не помечается как
   ранее действовавшее.
3. `apm run tests` проверяет совпадение пяти статусов в требовании, навыке,
   справочнике процесса и каталоге шаблонов, а также наличие сценария для
   отклонённого решения.
4. Регрессионный сценарий нового журнала проверяет типизированный путь и имя
   файла, сохранение существующего соглашения и предметное соответствие записи
   виду журнала.
5. Запись без раздела о способе проверки принимается, если у решения нет
   проверяемого критерия успеха.
6. Решение, отсеявшее варианты по правилу проекта без сравнения достоинств и
   недостатков, записывается в краткой форме и называет отвергнутые варианты и
   условие отсева.
7. Решение, принятое агентом без участия человека, записывается в полной форме.
8. При настройке исполнителя или сохранении согласованного допуска источников
   продукт выбирает предусмотренный артефакт настройки или разрешения.
   Долговечность этих сведений сама по себе не приводит к созданию DR.
9. Выбор существенного свойства поставляемого продукта или договорённости
   участников о поставке проходит оценку значимости после определения области
   решения по концепции проекта.
10. При повторной настройке продукт обнаруживает слишком широкую формулировку
    существующего договора и исправляет её после требуемого подтверждения,
    сохраняя путь, реестр и записи журнала.
11. Явно принятое владельцем соглашение, расходящееся с областью DR, выносится на
    его решение до изменения. Корректный договор сохраняется без переписывания.
