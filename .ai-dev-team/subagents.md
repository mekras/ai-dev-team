# Инструкции по работе с подагентами

Эта процедура действует для всего проекта ai-dev-team. Прочитай её полностью
при подготовке корневого входа по `AGENTS.md`. Все пути и команды ниже заданы
от корня проекта. Проектные условия берутся из локальной политики.

## Рабочая политика подагентов

До чтения рабочих входов, исследования или реализации сначала проверьте,
существует ли `.ai-dev-team/local/subagents.local.toml`, и прочитайте его.
Политика в этом файле — единственный источник проектных условий передачи,
прямого выполнения, ограничений входа, приёмки и эскалации.

Чтение этой политики при обычном выполнении не превращает задачу в настройку
или проверку политики. Не запускайте процедуру настройки, если пользователь
не поручил настроить, изменить или проверить саму политику.

Разделяйте родительскую задачу и каждое действие или подзадачу внутри неё.
Сразу после чтения политики и до первого чтения предметного входа,
исследования или реализации примите одно краткое решение о маршруте и
сохраните его во внешнем следе текущей сессии. Используйте промежуточное
сообщение пользователю, встроенный журнал хода или запись задачи запускателя
в зависимости от возможностей оснастки. Итоговый ответ не заменяет такой
предварительный след. Не запрашивайте для этой записи отдельного согласования.
Не раскрывайте внутренние рассуждения: достаточно строки «Маршрут» с
рассмотренным объёмом, исходом, предметным основанием и неопределённостью,
если она есть.

Определите результат, полномочия и границы всей родительской задачи, назовите
каждую кандидатную ограниченную подзадачу либо прямо укажите, что кандидатов
нет, и сопоставьте кандидаты с маршрутами из `[policy_runtime.routes]`. Исход
— `прямое выполнение`, `делегирование` или `маршрут не разрешён`. Предметное
основание охватывает пользу отдельного контекста, полномочия, независимость,
приёмку и полную стоимость. Одна отметка о чтении политики не заменяет этого
решения.

При прямом выполнении сохраните решение вместе с конкретной причиной.
При делегировании внесите то же решение в задачу запускателя, затем сохраните
созданную запись запуска и родительскую приёмку. Итоговый ответ может кратко
сослаться на предварительный след, но не подтверждает его временной порядок.
Отсутствие решения или следа — пропуск применения политики, даже если
предметный ответ оказался полезным.

Значение
`direct_execution_scope = "whole_parent_task"` означает только, что саму
родительскую задачу целиком не передают. Оно не отменяет отдельного
рассмотрения подходящей ограниченной read-only подзадачи. Значение
`subtask_routing = "match_each_bounded_subtask"` требует отдельно проверить
такую подзадачу и её маршрут. Если маршрут оправдан, подзадачу можно передать
с собственными входами, запретами и приёмкой. Для рассматриваемой ограниченной
read-only подзадачи дочернему исполнителю запрещены запись, утверждение решения
и расширение области. Это ограничение относится только к этому маршруту и не
отменяет отдельный контракт класса, который явно разрешает ограниченную запись.
Независимо от класса дочерний исполнитель не изменяет защищённые источники,
не утверждает решения и не расширяет область. Родитель сохраняет запись в
защищённых источниках, утверждение решений и итоговую приёмку результата.
Микрозадачи не декомпозируйте искусственно. Для прямого выполнения свяжите
причину с конкретными свойствами рассматриваемой подзадачи и полной стоимостью
передачи: например, с малым явным входом, отсутствием требуемой независимости
или отдельного полномочия, а также с тем, что постановка, вход и приёмка не
окупаются известной пользой. Само `whole_parent_task` и формат итогового ответа
не являются причиной прямого выполнения. Если для выделения или передачи нет
оправданного маршрута либо постановка, вход и приёмка дороже ожидаемой пользы,
соответствующий объём работы выполняет родитель. При недостатке сведений не
приписывайте прямому выполнению непроверенное преимущество: сохраните эту
неопределённость или выберите предусмотренный политикой неразрешённый маршрут.

До самостоятельного исследования или реализации для каждой подзадачи, которую
после этой оценки признали оправданной для передачи, сопоставьте её с
маршрутами из `[policy_runtime.routes]`. Если маршрут совпал, выделите
ограниченную подзадачу и запустите его указанный класс через команду из
`launcher` с `--target`, равным `target`, передав все разрешённые рабочие
файлы явными
`--input`. До запуска проверьте фактическую VCS проекта и защиту выбранного
каталога временных данных. В этом Git-проекте используйте `--git-storage`:
запускатель проверит исключение данных запуска из Git. Для заранее проверенного
родителем места хранения используйте `--storage-verified` и сохраните основание
проверки. Этот флаг сам по себе не проверяет защиту каталога. Без одного из этих
флагов запуск запрещён. Не заменяйте запуск встроенным ожиданием или
неименованным вызовом подагента. Передайте ограниченную постановку через stdin:

```sh
printf '%s\n' '<ограниченная постановка>' |
  "$launcher" "$execution_class" --target "$target" \
    --input input-a.md --git-storage
```

Пустой stdin не является задачей и запускатель отклоняет его до обращения к
модели. Дождитесь терминального кода запускателя и прочитайте
созданную запись запуска до использования результата или перехода к прямой
работе. После содержательной проверки внесите в запись отдельные поля
`acceptance` и `quality_assessment` с критериями и материалами проверки.
Используйте результат класса только после родительской приёмки и сохраните
технический след до завершения всей родительской задачи. После приёмки и
завершения задачи удалите временные данные каждого её запуска командой
`"$launcher" --finish-task <run.json> --run-id <UUID>`.
Для неуспешного запуска сначала запишите отклонённую приёмку и оценку причины
отказа. Возможность CLI удалить такой запуск без приёмки не отменяет это
правило. Не удаляйте данные работающего или чужого запуска. Сохранение данных
после
завершения допустимо только по явному поручению, заданному через `--retain-for`.
Если передача отдельной подзадачи не оправдана, сохраните
причину прямого выполнения в итоговом следе. Отделяйте отказ дочернего процесса
от успешного процесса без требуемого клиентского свидетельства модели или
усилия: для первого применяйте `execution_failure`, для второго —
`unconfirmed_model`. Несовпадение назначения и противоречие источников
фиксируйте отдельными статусами и не объявляйте подтверждением. Не повторяйте
тот же запуск без изменения маршрута или среды. При недоступном маршруте
действуйте по `unavailable_route`; не объявляйте настройку, модель, качество
или экономию подтверждёнными без требуемого в политике свидетельства.

Перед выбором маршрута сопоставьте его с фактическими параметрами текущего
родителя из метаданных активной сессии. Поля `policy_design` и сохранённые
назначения описывают историческое основание настройки, а не текущую модель или
усилие. Если параметры неизвестны, сравнение остаётся нерешённым и это нельзя
выдавать за подтверждение. Не называйте передачу лучшей, более дешёвой или
более качественной по непроверенному сравнению с родителем. Передача остаётся
допустимой, если её предметное основание не зависит от неизвестного параметра:
известны полномочия и приёмка, а отдельный контекст, независимость либо иная
польза оправдывают полную стоимость. В таком случае сохраните неизвестный
параметр и явно укажите, что сравнение не было основанием выбора. Если без
сравнения нельзя обосновать ни передачу, ни прямое выполнение, зафиксируйте
маршрут как неразрешённый и запросите недостающее свидетельство либо выполните
предусмотренную политикой эскалацию. Если модель или усилие родителя изменились,
предыдущее сравнение недействительно и маршрут нужно оценить заново.
При проверке запуска используйте указанную в `policy_runtime`
`comparison_evidence_level`. Собственный rollout или база Codex подтверждают
клиентский маршрут в границе `client_execution`, даже если серверное
свидетельство отсутствует. Для модели и усилия сохраняйте источник, поток и
границу отдельно. Несовпадение назначения, противоречие источников и отсутствие
данных требуют разных статусов и не считаются подтверждением.
Совпадение моделей само по себе не оправдывает передачу и не запрещает её:
проверьте пользу отделённого контекста, полномочия, требуемую независимость,
приёмку и полную стоимость именно для выделенной подзадачи.

## Экономное использование подагентов

Цель маршрутизации подагентов: снизить расход основных лимитов и сохранить
качество за счёт узкого делегирования, проверки и редкой эскалации.

Общие правила действуют в любой оснастке. Ветви запуска описывают только
механику конкретной оснастки. Идентификаторы моделей закреплены не здесь, а в
личной настройке подагентов.

### Общие правила

- Подготовку самоприменения и маршрутизацию перед запуском подагента выполняет
  родительский агент. Запущенный подагент считает эти шаги выполненными
  родителем, не повторяет их и сразу исполняет переданное поручение.
- Канонический источник предметного выбора роли — `ait-routing`.
  `technical-writer` используй только для проверки русского текста в явно
  переданных исходниках навыков, а `documentation-reader` — только для проверки
  документации от лица заданного профиля читателя.
- Обычную работу, финальный ответ и приёмку результата выполняет родительский
  агент на модели активной сессии.
- Каждое делегирование относи к одному из четырёх классов выполнения:
  - `cheap_readonly_research` — узкий поиск, извлечение фактов, списки
    кандидатов и малые сводки по явно переданным файлам. Предпочитай этот
    класс, пока его достаточно: он рассчитан на самую дешёвую доступную
    модель.
  - `mechanical_readonly` — низкорисковая механическая работа без записи,
    когда делегирование дешевле прямого выполнения родителем, а результат
    проверяется автоматически или по небольшому различию.
  - `small_write_patch` — малая обратимая правка с правом записи, когда
    родитель явно указал точные файлы или узкую область записи. В этом классе
    подагент не меняет `AGENTS.md`, `.apm/`, требования, архитектурные
    решения, корпус знаний и другие источники истины. Одновременно работает не
    более одного пишущего подагента, родитель проверяет различия и выполняет
    подходящую детерминированную проверку.
  - `deep_review` — глубокий анализ или редкая независимая проверка правил,
    ролей, навыков, архитектурных решений и других источников истины, ошибка в
    которых повлияет на будущие задачи или потребует дорогой переделки.
- Модель, усилие и режим песочницы класса бери из личной настройки
  `.ai-dev-team/local/subagents.local.toml` по цели активной оснастки. Не
  закрепляй идентификаторы моделей в этом файле и не подставляй их по памяти.
- Если для класса нет назначения под активную оснастку, считай класс
  ненастроенным: выполни задачу родителем или запроси решение пользователя. Не
  подменяй отсутствующее назначение моделью другой оснастки.
- Личная настройка `.ai-dev-team/local/subagents.local.toml` не входит в Git:
  общей настройки в репозитории нет, каждый заводит свою из образца
  `.agents/skills/ai-setup-subagents/assets/subagents.local.toml.sample`. Если
  файла нет, считай маршрутизацию подагентов ненастроенной, а не ошибкой.
- Не делегируй микрозадачи, широкие решения, финальную приёмку результата,
  работу с неясными критериями или изменения файлов без явного контракта.
- Максимум: два параллельных подагента и один уровень вложенности. Подагентам
  запрещено запускать собственных подагентов.
- Каждый результат подагента должен быть структурирован и содержать `status`,
  `items`, `evidence`, `confidence`, `risk`, `open_questions` и
  `escalation_needed`.
- `escalation_needed` означает, что подагент не может безопасно завершить
  поручение из-за недостающих входов, конфликта контракта, необходимости
  расширить область или получить внешнее решение. Решение человека, которое
  следует из завершённой проверки, фиксируй в `items` или `open_questions`: само
  по себе оно не требует эскалации.
- Родительский агент отклоняет результат подагента, если тот расширил область,
  не дал ссылок на файлы или источники, вернул незавершённый статус или запрос
  эскалации, либо не обосновал указанную уверенность свидетельствами.
  Противоречия, неуверенность и открытые вопросы в проверяемом материале считай
  находками, а не причиной отклонения завершённого результата.
- Не повторяй запуск подагента автоматически. Перед новым запуском установи
  причину по журналу и измени хотя бы одно условие: контракт, входные данные,
  настройку или адаптер. Зафиксируй причину и изменение условия, без такого
  изменения выполни задачу родителем или запроси решение пользователя.
- Не запускай одну задачу одновременно на нескольких моделях, если пользователь
  или проектное правило явно не требуют независимого сравнения.
- Разделяй исход процесса, подтверждение назначения и приёмку результата по
  локальной политике. Код `0` сам по себе не подтверждает модель и усилие.
  При отсутствии свидетельства используй `unconfirmed_model` и правило
  `result_acceptance`, не подменяй его отказом процесса `execution_failure`.

### Запуск в Codex

- Инструкцию классу выполнения передавай через стандартный ввод. Указывай цель
  `codex`, только явно нужные входные файлы через `--input`, личную настройку
  через `--config` и каталог журналов через `--out`.

  ```bash
  printf '%s\n' '<инструкция>' |
    .agents/skills/ai-setup-subagents/scripts/run-execution-class <класс> \
      --target codex \
      --config .ai-dev-team/local/subagents.local.toml \
      --input <файл> \
      --out .ai-dev-team/local/subagents \
      --git-storage
  ```

- Для `small_write_patch` каждый `--input` должен быть разрешённой целью
  записи, не передавай подагенту справочные файлы, которые он не вправе менять.
- Если задача требует именованную роль из таблицы `[roles]`, используй
  `run-subagent-role` с теми же ключами, кроме `--target`.
- Класс `cheap_readonly_research` назначен на модель с отдельным лимитом: этот
  класс не расходует общий пул остальных моделей оснастки.
- Усилие `max` требует отдельного обоснования. Усилие `ultra` не используй.
- Расход проверяй командой `tools/codex-usage-report --line <журнал-jsonl>`.
- Встроенный поток подагента используй только для параллельности или изоляции
  контекста, когда конкретная роль и модель не требуются. Не выдавай такой
  поток за ролевую маршрутизацию. При наследовании модели учитывай расход как
  расход родительской модели.
- Сохраняй `tools/codex-model-subagent` и `tools/codex-spark-subagent` только
  как совместимые скрипты запуска: они не гарантируют, что контракт роли
  применён полностью.

### Запуск в Claude Code

- Классы без записи запускай тем же `run-execution-class` с `--target claude` и
  остальными ключами из ветви Codex. Адаптер Claude поддерживает только режим
  `read-only`.
- Класса `small_write_patch` в этой оснастке нет: малую правку выполняет
  родительский агент сам. Не заменяй родителя подагентом с правом записи.
- Встроенное средство `Agent` считай ролевой маршрутизацией только тогда, когда
  в вызове явно заданы тип агента из `.claude/agents/` и модель, выбранная по
  классу выполнения. Без явного указания модель наследуется от родителя, и
  расход учитывай как расход родительской модели.
- Отдельного отчёта о расходе здесь нет. Для запуска через `run-execution-class`
  расход бери из поля `usage` записи запуска, а для встроенного средства `Agent`
  относи его к выбранной модели.
