## Существенные сведения источника

Редакция 2025 года добавила к трём прежним разделам книги три новых: «Паттерны
дизайна API», «HTTP API и архитектурные принципы REST», «SDK и UI-библиотеки»,
плюс две новые главы введения (выбор решений, API-first).

Значимые группы новых утверждений:

- `APIB-072`–`APIB-076` — выбор подхода и API-first;
- `APIB-077`–`APIB-109` — паттерны: устойчивость к исключениям, авторизация
  вызовов, синхронизация и консистентность, асинхронность, перебор списков, push
  против опроса и `webhook`, массовые операции, частичные обновления,
  предсказуемость и деградация;
- `APIB-110`–`APIB-152` — HTTP API: терминология («REST API» без консистентного
  определения, рабочий термин «HTTP API»), выбор технологии, семантика RFC 9110,
  статус-коды, ошибки, организация сервисов, URL и CRUD, итоговые рекомендации;
- `APIB-153`–`APIB-185` — SDK и UI-библиотеки: слои задач SDK, пределы
  кодогенерации, UI-компоненты и кастомизация, декомпозиция и MV\*,
  Backend-Driven UI, разделяемые ресурсы экрана, вычисляемые свойства.

## Находки

### Severity: Medium — три новых предметных области не были отражены в продукте

Документ: `.apm/skills/ait-architecture/references/api-design.md`,
`.apm/skills/ait-architecture/SKILL.md`

Первичные данные: `APIB-072`–`APIB-185`, проверка `2026-07-17`

Класс: новое существенное сведение

Факт источника: паттерны дизайна API, современная семантика HTTP API и
дисциплина SDK/UI-библиотек отсутствовали в справке, построенной по редакции
2023 года.

Статус переноса: `apply_now`. Что сделано: в `api-design.md` добавлены блок
API-first и разделы «Паттерны дизайна API», «HTTP API: терминология и выбор
технологии», «HTTP API: семантика и организация», «SDK и UI-библиотеки»;
описание справки в `SKILL.md` расширено. **Выполнено.**

### Severity: Medium — конфликт рекомендаций источников и терминологическая коллизия

Документ: `knowledge/concepts.yml` (запись `http-api`),
`.apm/skills/ait-architecture/references/api-design.md`

Первичные данные: `APIB-113`, `APIB-120`–`APIB-123`, `APIB-138`;
`RADR-073`–`RADR-081`, проверка `2026-07-17`

Класс: противоречие источников

Факт источников: RADR предписывает не помещать версию API в URI, APIB
рекомендует размещать её в пути; RADR называет «REST API» тот же практический
объект, который APIB называет «HTTP API».

Статус переноса: `apply_now` (решение владельца `2026-07-17`). Что сделано:
заведена запись согласования `http-api` (ортогональность осей «стиль — протокол
— транспорт», исключение RPC-туннелей, синонимия по источникам); закреплено
правило области применения — свод RADR действует, когда проект явно зафиксировал
решением ресурсоориентированный REST-дизайн и RADR как конвенцию; внутри области
приоритет: спецификации HTTP (RFC 9110/9111) → RADR в вопросах стиля → APIB; без
такого решения вариант по умолчанию — APIB (версия в пути). Правило внесено в
оба места `api-design.md`. **Выполнено.**

### Severity: Low — битые ссылки на удалённые `legacy-statements.md`

Документ: 12 файлов `.apm/skills/` вне области задачи (`ait-sec-*`,

Класс: улучшение качества (дефект обнаружен при аудите, не вызван обновлением
APIB)

Статус переноса: `owner_decision` — зафиксировано в `BACKLOG.md` («Битые ссылки
на удалённые файлы `legacy-statements.md` в навыках»). В зоне задачи
(`api-design.md`) ссылки исправлены на действующие пути.

### Severity: Low — стабильное срабатывание знаний за пределами навыка архитектуры

Документ: `ait-sec-threat-modeling/SKILL.md` (`APIB-099`, `APIB-152`),
`ait-architecture/references/reliability.md` (`APIB-108`, `APIB-109`),
`ait-interface-design/SKILL.md` (`APIB-161`–`APIB-185`)

Класс: новое сведение, частично покрыто справкой по API

Статус переноса: `apply_now` (решение владельца `2026-07-17`: критерий — не
удобство, а надёжность срабатывания; дублирования содержания избегать, но
стабильное применение знаний в нужных случаях важнее). Что сделано: в три
профильных места добавлены указатели с условием срабатывания на разделы
`api-design.md` — моделирование угроз публичного или партнёрского API →
безопасность `webhook` и типовые уязвимости HTTP API; надёжность API →
устойчивость к исключениям и деградация; поставка интерфейса как SDK или
UI-библиотеки → раздел «SDK и UI-библиотеки». Содержание живёт в одном месте
(`api-design.md`), профильные навыки ведут к нему явным условием. **Выполнено.**
