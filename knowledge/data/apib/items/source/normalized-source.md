## Ограничение качества материала

- Главы актуальной редакции получены как markdown-исходники книги, без прогона
  через PDF; искажений вёрстки, колонтитулов и порядка блоков нет.
- Прежняя текстовая выгрузка (снимок 2023-04-09) была получена утилитой
  `pdftotext -layout`; в ней колонтитулы и номера страниц перемешаны с текстом,
  а блоки кода и иллюстрации могли идти с искажением порядка. Эта выгрузка
  сохранена только для трассируемости уже извлечённых утверждений и не
  используется как источник новых утверждений.

## Структура книги (редакция 2025-10-11, шесть разделов)

Книга проводит читателя по жизненному циклу API — от замысла до сопровождения
зрелого продукта — и держит сквозную мысль: API есть формальное обязательство
связывать программируемые контексты, поэтому ошибки проектирования и нарушение
совместимости умножаются на число потребителей. По сравнению с редакцией
2023-04-09 структура выросла с трёх содержательных разделов до шести: в введении
добавились две главы о выборе подхода к разработке API, а между проектированием
и обратной совместимостью встал новый раздел о паттернах дизайна, за обратной
совместимостью — новые разделы про HTTP API и REST и про SDK и UI-библиотеки.

### Введение (8 глав)

- «О структуре этой книги»: шесть разделов и тезис о первичности продуктового
  раздела.
- «Определение API»: смысловое определение API как формального обязательства
  связывать программируемые контексты; потребители API — инженеры.
- «Критерии качества API»: очевидность, читаемость, консистентность;
  предупреждение об оверинжиниринге.
- «Выбор подхода к разработке API» _(новая глава)_: как решить, нужен ли API
  вообще и какой технологический подход выбрать под задачу.
- «API-first подход» _(новая глава)_: проектирование API раньше и отдельно от
  реализации как инженерная практика, а не только философия.
- «Обратная совместимость»: совместимость как временна́я характеристика качества
  и «скрытый налог» на потребителей при сломе совместимости.
- «О версионировании»: semver и эквивалентность «мажорная версия» = «обратно
  несовместимое изменение».
- «Условные обозначения и терминология»: нейтральный термин «сущность», нотация
  JSON-over-HTTP и C-подобный псевдокод примеров.

### Раздел I. Проектирование API (5 глав)

- «Пирамида контекстов API»: алгоритм проектирования из четырёх шагов сверху
  вниз.
- «Определение области применения»: четырёхкратный вопрос «какую проблему мы
  решаем?» с ударением на каждом слове.
- «Разделение уровней абстракции»: цели изоляции уровней и инструмент «дерево
  потоков данных».
- «Разграничение областей ответственности»: формулирование назначения сущностей
  и проверка номенклатуры через сценарии использования.
- «Описание конечных интерфейсов»: набор практических правил именования и
  проектирования эндпойнтов (явность, идемпотентность, информативные ошибки,
  пагинация, безопасность, локализация).

### Раздел II. Паттерны дизайна API (11 глав, новый раздел)

- «О паттернах проектирования в контексте API»: чем задачи дизайна API
  отличаются от классических паттернов ПО; три сквозных принципа (устойчивость к
  сбоям, недоверие к партнёрам, недетерминированные задержки).
- «Аутентификация партнёров и авторизация вызовов API»: разграничение личности
  приложения, пользователя и партнёра.
- «Стратегии синхронизации»: подходы к синхронизации состояния между клиентом и
  сервером.
- «Слабая консистентность»: работа с задержкой и неполной согласованностью
  данных на уровне API.
- «Асинхронность и управление временем»: паттерны асинхронных операций и учёт
  временных характеристик выполнения.
- «Списки и организация доступа к ним»: пагинация, фильтрация и сортировка как
  проектные решения, а не техническая деталь.
- «Двунаправленные потоки данных. Push и poll-модели»: выбор и комбинирование
  моделей доставки данных клиенту.
- «Мультиплексирование сообщений. Асинхронная обработка событий»: организация
  событийных каналов и порядок обработки сообщений.
- «Атомарность массовых изменений»: гарантии целостности при пакетных операциях.
- «Частичные обновления»: проектирование операций изменения части ресурса.
- «Деградация и предсказуемость»: поведение API при частичном отказе
  зависимостей.

### Раздел III. Обратная совместимость (7 глав)

- «Постановка проблемы обратной совместимости»: совместимость как функциональная
  стабильность во времени; три процесса её размывания.
- «О ватерлинии айсберга»: гигиенический минимум публичной поверхности API и
  фиксация неявных договорённостей.
- «Расширение через абстрагирование»: вариационный анализ «что, если?» и
  расширение через подключение реализаций.
- «Сильная связность и сопутствующие проблемы»: как сильная связность разрушает
  чистоту интерфейсов.
- «Слабая связность»: параметризация взаимодействия для разрыва жёстких
  зависимостей.
- «Интерфейсы как универсальный паттерн»: обобщение приёмов расширения; связь с
  принципами SOLID.
- «Блокнот душевного покоя»: конкретные рекомендации по совместимым изменениям,
  тестирование формальных интерфейсов, изоляция зависимостей.

### Раздел IV. HTTP API и архитектурные принципы REST (8 глав, новый раздел)

- «О концепции HTTP API. Парадигмы разработки клиент-серверного взаимодействия»:
  место HTTP API среди других способов организации взаимодействия.
- «Преимущества и недостатки HTTP API в сравнении с альтернативными
  технологиями»: когда HTTP API — уместный выбор, а когда нет.
- «Мифология REST»: разбор распространённых заблуждений о REST.
- «Составляющие HTTP запросов и их семантика»: методы, заголовки, коды состояния
  и их точное назначение.
- «Организация HTTP API согласно принципам REST»: практическое применение
  архитектурного стиля REST.
- «Разработка номенклатуры URL ресурсов. CRUD-операции»: правила именования
  ресурсов и сопоставления операций с HTTP-методами.
- «Работа с ошибками в HTTP API»: проектирование информативных и единообразных
  ошибок.
- «Заключительные положения и общие рекомендации»: сводные практические
  рекомендации раздела.

### Раздел V. SDK и UI-библиотеки (9 глав, новый раздел)

- «Терминология. Обзор технологий разработки SDK»: понятийный аппарат раздела и
  ландшафт технологий.
- «SDK: проблемы и решения»: типичные задачи разработки клиентских библиотек.
- «Проблемы встраивания UI-компонентов»: специфика API, предоставляющих не
  данные, а интерфейсные компоненты.
- «Декомпозиция UI-компонентов»: принципы разбиения UI на переиспользуемые
  части.
- «MV\*-фреймворки»: архитектурные паттерны разделения модели, представления и
  логики в SDK.
- «Backend-Driven UI»: управление представлением с backend-стороны.
- «Разделяемые ресурсы и асинхронные блокировки»: координация доступа к общим
  ресурсам в клиентских библиотеках.
- «Вычисляемые свойства»: проектирование производных данных в SDK.
- «Заключение»: итоги раздела.

### Раздел VI. API как продукт (13 глав)

- «Продукт API»: API как полноценный, но специфический продукт; пирамида
  аудитории (пользователи — бизнес — разработчики).
- «Бизнес-модели API»: прямые и косвенные модели монетизации.
- «Формирование продуктового видения»: тройная аудитория и недоступность
  дешёвого MVP для API.
- «Взаимодействие с разработчиками»: рациональная аудитория, каналы технопиара,
  Open Source, профи и новички.
- «Взаимодействие с бизнес-аудиторией»: лояльность бизнеса и трудность объяснить
  ценность API.
- «Линейка сервисов API»: набор продуктов в двух измерениях (горизонтальном и
  вертикальном).
- «Ключевые показатели эффективности API»: KPI по целевым действиям, SLA и
  повышенный запас прочности.
- «Идентификация пользователей и борьба с фродом»: идентификация приложений и
  владельцев, ненадёжность API-ключей, подсчёт по IP.
- «Технические способы борьбы с несанкционированным доступом к API»: три шага
  антифрода и скудость средств бана.
- «Поддержка пользователей API»: высокая планка к специалистам, доминирование
  вопросов новичков, роль комьюнити.
- «Документация»: документация как лицо продукта; виды документации.
- «Тестовая среда»: необходимость тестового API и два подхода к нему.
- «Управление ожиданиями»: золотое правило версий, поддержка платформ,
  публикация роадмапов.

## Связь с проектом

Нормализованный слой служит картой для извлечения утверждений
(`knowledge/data/apib/items/text/statements.yml`, единая нумерация `APIB-*` для
обеих редакций) и для анализа влияния на навыки проекта, связанные с
архитектурой, требованиями, технической документацией и управлением проектом.
Покрытие по главам см. `knowledge/data/apib/source-map.yml`: главы,
отсутствовавшие в редакции 2023-04-09 (два новых введения и три новых раздела),
помечены как `pending` до отдельного прохода `kc-statements`.
