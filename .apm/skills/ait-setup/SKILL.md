# Навык: настройка проекта

## Назначение

Навык помогает настроить новый проект или перенастроить существующий проект под
`ai-dev-team` через короткий диалог и минимальные безопасные изменения.

Главная роль `ait-setup` — не повторять процедуры соседних навыков, а задать
обязательный порядок проверки, маршрутизации и вопросов к человеку.

## Когда применять

Применяй навык, если пользователь просит:

- настроить проект;
- перенастроить существующий проект;
- обновить проект под актуальные правила `ai-dev-team`;
- перейти на новую версию `ai-dev-team` и пересмотреть проект под её изменения;
- начать новый проект;
- инициализировать проект;
- подготовить стартовые файлы проекта;
- завести базовый `README.md`, `LICENSE`, `AGENTS.md`, `.gitignore` и при
  необходимости `CHANGELOG.md`;
- подготовить новый репозиторий к работе с агентами.

Не применяй навык для обычной правки одного существующего файла, настройки
только подагентов, создания одной лицензии или полного проектирования
документации.

## Режим по умолчанию

По умолчанию работай в диалоговом режиме: задавай по одному обязательному
вопросу за ход и не создавай окончательные файлы, пока не собраны блокирующие
решения человека.

Диалоговый режим означает, что агент не принимает проектные решения молча. Перед
новым решением, которое меняет маршрут настройки, структуру проекта, статус
корпуса знаний, лицензию или клиентские инструкции, сформулируй предложение и
получи подтверждение человека. Перед первой записью в ещё не согласованной
области назови файлы, смысл изменений и причину.

Если человек явно поручил автономно выполнить согласованную серию однотипных
правок, зафиксируй её границы: разрешённые действия и файлы, запреты и критерий
завершения. В этой области выполняй последующие безопасные действия без новых
вопросов. Остановиться можно только перед новым решением владельца, выходом за
границы серии, конфликтом с чужими изменениями или конкретным внешним блокером.
Промежуточный статус не завершает такую серию: сообщай его в комментарии и сразу
переходи к ближайшему безопасному действию. Финальный ответ допустим только
после завершения серии или с точной причиной блокировки.

## Обязательный порядок

1. Сначала примени `ai-audit-project`: проверь текущие стартовые файлы, правила
   проекта для агента и явные расхождения с актуальными правилами продукта. Если
   проект подключает `ai-dev-team` через APM либо заявляет установленную версию
   в файле состояния или `apm.lock.yaml`, до выводов о версии и до проектных
   вопросов выполни `apm audit --ci`. Ненулевой результат, дрейф активного
   `ait-setup`, его справок или корневого пакета блокирует настройку. Не считай
   версию из lock-файла доказательством фактически развёрнутой копии и не
   продолжай диалог до отдельного исправления установки.
2. По результатам аудита первым проектным вопросом выясни рабочий контекст:
   коммерческий, некоммерческий, смешанный или иной, описанный человеком. Это не
   юридическая квалификация и не автоматический порядок факторов для решений.
   Сохрани подтверждённый ответ в `setup.operating_context` файла состояния.
   Затем определи профиль проекта по разделу «Профиль проекта» в
   `references/setup-dialogue.md`: формы продукта, основных пользователей,
   способы взаимодействия и поставки. Профиль может включать несколько форм. Не
   продолжай настройку по общему ответу вроде «среда для работы», пока не
   установлено, что именно проект создаёт и как этим пользуются. Если профиль
   включает публикуемую коллекцию APM, обязательно примени `ai-setup-apm` и не
   дублируй его проверку структуры, `apm.yml` и процесса `apm run tests` внутри
   `ait-setup`. Определяй этот маршрут по профилю проекта и публикуемым
   примитивам APM, а не по одному найденному файлу.
3. Если задача — переход на новую версию `ai-dev-team` (человек просит обновить
   проект под новую версию либо аудит показал смену версии продукта), проведи
   пересмотр по `references/setup-dialogue.md`, раздел «Обновление версии
   продукта», прежде чем продолжать остальные шаги настройки.
4. Если в корне проекта уже есть `.ai-dev-team-state.yml`, сначала прочитай его
   и используй как источник ранее принятых параметров настройки проекта:
   рабочего контекста, профиля, видимости, Git, схемы сообщений коммитов,
   журнала изменений, журналов решений, корпуса знаний и состояния клиентских
   инструкций, а для проекта с интерфейсом — уровня интерфейсных проверок. Не
   дублируй эти сведения в `AGENTS.md`, если они нужны только самому
   `ait-setup`; схема сообщений коммитов и уровень интерфейсных проверок
   являются рабочими правилами и должны быть доступны агенту во время предметной
   задачи.
5. Собери недостающие сведения по `references/setup-dialogue.md`: один
   блокирующий вопрос за ход, начиная с самого раннего решения, без которого
   нельзя безопасно продолжить. Каждый вопрос задавай по разделу «Договор
   вопросов»: объясни назначение решения и последствия вариантов, используй
   доступный механизм выбора оснастки, а при допустимом текстовом выборе
   сохраняй номера вариантов и разрешай ответить номером. Если оснастка
   запрещает текстовые вопросы с несколькими вариантами и не даёт разрешённого
   селектора, не перечисляй варианты в сообщении и не подменяй меню
   рекомендацией одного из них: выясняй выбор последовательными короткими
   вопросами об одном наблюдаемом свойстве результата.
6. Если проект подключён к `ai-dev-team` через APM как потребитель, настрой
   клиентские инструкции по правилам `references/setup-dialogue.md`: сначала
   согласуй сохранение рукописных локальных правил из `AGENTS.md` или
   `CLAUDE.md` в локальном слое проекта. Обновляй клиентские инструкции через
   реальную компиляцию только для уже сгенерированных файлов или после
   отдельного явного решения человека заменить рукописный файл сгенерированным.
   Не выноси `apm compile --dry-run` в обычный следующий шаг, если человек не
   просит диагностировать генерацию или риск перезаписи.
7. Для `README.md` применяй `ait-readme`. Основного читателя и его первое
   действие сначала выведи из подтверждённого профиля проекта и найденных
   пользовательских сценариев. Не задавай отдельный общий вопрос о читателе,
   если профиль уже даёт эти сведения. Если остаётся развилка, которая меняет
   основной сценарий `README.md`, задай один вопрос о конкретной роли или первом
   действии, а не предлагай общий ответ «пользователь».
8. Для `AGENTS.md` применяй `ai-agents-md-maintenance`, но держи его коротким
   машинным входом: локальные рабочие правила, проектные границы и ссылки на
   нестандартные источники. Параметры настройки проекта, которые нужны только
   `ait-setup`, сохраняй в `.ai-dev-team-state.yml`. Если проект использует Git,
   а применимые инструкции не задают политику добавления изменений в индекс,
   предложи человеку отдельно выбрать один из вариантов `ai-setup-project`: все
   неигнорируемые изменения или только изменения агента в текущей задаче. Не
   выбирай вариант молча; после решения передай запись правила в
   `ai-agents-md-maintenance`.
9. Если проект использует Git, а схема сообщений коммитов ещё не закреплена,
   получи выбор `conventional-commits`, `gitmoji` или `pro-git` по правилам
   взаимодействия из `references/setup-dialogue.md`. Показывай эти варианты в
   селекторе или в разрешённом нумерованном текстовом выборе. Если оба способа
   недоступны, сначала спроси, нужны ли сообщения для автоматического
   определения версии и журнала изменений, не называя схем. Следующий короткий
   вопрос выбирай по ответу и подтверждай сопоставленную схему отдельно. Не
   выбирай вариант молча. Сохрани решение в `setup.commit_messages` и передай
   рабочее правило в `ai-agents-md-maintenance`. Для Gitmoji отдельно спроси
   формат `unicode` или `shortcode`.
10. Для журнала изменений:
    - если в проекте уже есть `CHANGELOG.md`, `NEWS.md` или `HISTORY.md`,
      предложи закрепить правило его сопровождения через `ait-changelog`;
    - если журнала нет и в `.ai-dev-team-state.yml` не зафиксирован явный отказ,
      предложи создать `CHANGELOG.md` как дополнительный стартовый файл;
    - если пользователь отказался от журнала изменений, зафиксируй это решение в
      `.ai-dev-team-state.yml`, чтобы не предлагать журнал повторно без нового
      запроса человека.

11. Для корпуса знаний:
    - если корпус уже есть, применяй `kc-setup`;
    - если корпуса нет, предложи создать его через `kc-setup`;
    - если пользователь отказался от корпуса, зафиксируй это решение в
      `.ai-dev-team-state.yml`, чтобы не задавать тот же вопрос повторно без
      нового запроса человека.

12. Для журналов решений (по `ait-decisions`):
    - проверь поле `setup.decision_records` в `.ai-dev-team-state.yml`; если в
      нём не зафиксирован явный отказ, предложи завести подходящие журналы
      (например, ADR); для каждого нового журнала последовательно согласуй вид и
      предметную границу, путь, формат имени записи, затем договор журнала в
      `README.md` и параметры в файле состояния;
    - для типовых новых журналов предлагай типизированные путь и имя:
      `docs/<ВИД>/` и `?DR-NNNN.md`; существующее соглашение проекта не меняй
      без отдельного решения о миграции;
    - не создавай первую запись ради инициализации журнала: она появляется
      только для одного значимого решения соответствующего вида;
    - при настройке проекта или первом значимом решении выясни порядок
      применимых факторов для проектных решений: сроки, риски, стоимость во
      времени, сопровождение, обратимость, влияние на пользователей или рабочие
      процессы и обязательные ограничения. Для некоммерческого контекста не
      предлагай сроки, стоимость и сопровождение как важные по умолчанию.
      Уточняй их применимость, только если подтверждены ограниченный бюджет,
      ограниченное добровольческое время, внешний срок или другое относящееся к
      проекту условие. Отдельно предложи закрепить выбранный порядок как
      операционное правило в `AGENTS.md`, а долговечное обоснование — отдельной
      ODR, если оно требуется;
    - если пользователь отказался, зафиксируй это решение в
      `.ai-dev-team-state.yml`, чтобы не предлагать журналы повторно без нового
      запроса человека.

13. Если профиль проекта содержит пользовательский интерфейс, объясни три уровня
    интерфейсных проверок по `references/setup-dialogue.md` и предложи выбрать
    `required`, `recommended` или `manual`. Закрепи выбор как рабочее правило
    проекта через `ai-agents-md-maintenance`, а служебное значение сохрани в
    `setup.interface_checks.level` файла состояния. При расхождении этих
    источников не выбирай значение молча.
14. Если настройка показывает, что для осмысленного `README.md` не хватает
    концепции проекта, сначала согласуй это с человеком и затем применяй
    `ait-docs-concept`.
15. Если проект использует Git, создавай или обновляй `.gitignore` минимально
    под известный стек и общие локальные артефакты. Если стек неизвестен,
    используй только универсальные безопасные исключения.
16. Создавай `LICENSE` только на основании выбранной лицензии или явного решения
    человека. Не подставляй текст лицензии по умолчанию.
17. После стартовых файлов проверь состояние политики подагентов через
    `ai-setup-subagents`. Запускай проверку без записи по прямому запросу, при
    отсутствии и политики, и зафиксированного отказа либо после истечения срока
    повторной проверки. Для настроенной политики предложи срок повторной
    проверки, по умолчанию 30 дней, и храни состояние по процедуре
    `ai-setup-subagents`. Исправление политики, фиксацию отказа и обновление
    даты успешной проверки подтверждай отдельно.
18. Если пользователь хочет приватный локальный слой знаний или неотслеживаемые
    локальные правила, применяй `ait-private-knowledge`.
19. Перед ответом «настройка закончена» проверь критерий завершения из
    `references/setup-dialogue.md`: по каждому обязательному направлению должен
    быть статус «сделано», «не требуется», «отложено решением человека» или
    «заблокировано вопросом». Если есть заблокированный пункт, настройка не
    закончена.
20. Перед завершением проверь, какие файлы созданы или изменены, и добавь новые
    отслеживаемые файлы в индекс Git, если проект использует Git и правила
    проекта не запрещают индексацию.

## Что читать дополнительно

- `references/setup-dialogue.md` — порядок вопросов, карта маршрутов по навыкам
  и правила для корпуса знаний.
- `assets/minimal-files.md` — рабочая заготовка минимального стартового набора.

## Границы

- Не дублируй процедуры `ai-audit-project`, `ai-setup-apm`, `ait-readme`,
  `ai-agents-md-maintenance`, `ait-changelog`, `ait-decisions`, `kc-setup` и
  `ai-setup-subagents` внутри этого навыка.
- Не пропускай стартовый аудит проекта даже для нового запроса «Настрой проект».
- Не сообщай, что версия `ai-dev-team` установлена или активна, только по записи
  в `.ai-dev-team-state.yml`, `apm.yml` или `apm.lock.yaml`. Для проекта с APM
  это требует успешного `apm audit --ci` без дрейфа активного `ait-setup`.
- Не маршрутизируй проект в `ai-setup-apm`, пока не определено, что текущая
  задача относится к публикуемой APM-поверхности проекта.
- Не передавай запросы «Обнови проект под новую версию ai-dev-team» и «Обнови
  проект под новую версию» в `ai-setup-apm`, если человек уже обновил
  установленную версию продукта и просит именно пересмотр проекта по журналу
  изменений.
- Не вноси файл, клиентскую инструкцию или проектное решение без подтверждения
  человека, кроме безопасных действий внутри явно согласованной автономной
  серии.
- Не считай перенос смысла рукописного `AGENTS.md` или `CLAUDE.md` в
  `.apm/instructions/**` разрешением перезаписать исходный рукописный файл через
  `apm compile`.
- Не поднимай `apm compile --dry-run` как штатный следующий шаг настройки для
  рукописных клиентских инструкций; это только явная диагностика риска
  генерации, когда она нужна для решения человека.
- Не создавай корпус знаний молча и не выбирай имя его папки без решения
  человека.
- Не создавай журнал изменений молча и не выбирай его формат без решения
  человека, если в проекте уже используется другой журнал или есть несколько
  кандидатов.
- Не используй `AGENTS.md` как хранилище ответов на анкету настройки, если эти
  сведения не нужны агенту в обычной предметной работе.
- Не предлагай корпус знаний повторно, если в `.ai-dev-team-state.yml` уже
  зафиксировано решение проекта работать без него.
- Не предлагай журнал изменений повторно, если в `.ai-dev-team-state.yml` уже
  зафиксировано решение проекта работать без него.
- Не предлагай журналы решений повторно, если поле `setup.decision_records` в
  `.ai-dev-team-state.yml` содержит `status: declined`.
- Не добавляй в `AGENTS.md` служебные параметры вроде видимости проекта, статуса
  Git или раздела «Проверки», если они нужны только маршруту `ait-setup` и не
  являются рабочими правилами проекта.
- Не создавай крупную структуру каталогов без отдельного обоснования.
- Не выдумывай концепцию, требования, архитектуру, стек, сроки, роли и
  бизнес-эффект.
- При обновлении версии не придумывай действия, которых нет в разделе «Действия
  при обновлении» журнала изменений продукта. Массовые правки требуют либо
  подтверждения каждого изменения, либо явного поручения автономно выполнить
  согласованную серию в названной области.
- Не записывай настоящие секреты в `AGENTS.md`, `.env`, локальные правила или
  другие текстовые файлы.

## Результат

Результатом работы должны быть:

- минимальные стартовые файлы проекта или вопросы, без которых их нельзя создать
  безопасно;
- установленный рабочий контекст проекта или один блокирующий вопрос для его
  уточнения;
- установленный профиль проекта или один блокирующий вопрос для его уточнения;
- статус обязательных направлений настройки: README, правила для агентов,
  клиентские инструкции, журнал изменений, журналы решений, корпус знаний,
  `.gitignore`, лицензия, подагенты, Git, схема сообщений коммитов и проверки;
- если менялись или подтверждались параметры настройки проекта, обновлённый
  `.ai-dev-team-state.yml`;
- явный список созданных и изменённых файлов;
- перечень применённых навыков и причин их выбора;
- список решений человека, которые были использованы;
- открытые вопросы и следующие безопасные шаги.

Для перехода на новую версию результат дополнительно содержит применённую версию
из `.ai-dev-team-state.yml`, целевую версию установленного продукта, перечень
рассмотренных действий из журнала изменений и решения человека по каждому из
них.
