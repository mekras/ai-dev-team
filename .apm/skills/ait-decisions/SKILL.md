# Навык: записи решений

Единая дисциплина записи значимых проектных решений для всех видов журналов:
архитектурные (ADR), организационные (ODR), по документации (DDR) и другие.
Набор видов открытый: состав и границы журналов определяет проект, новый вид не
требует изменения этого навыка. Профильные навыки задают только предметную ось —
что считать значимым решением своего вида (требования `ФТ-7`–`ФТ-9`, `КАЧ-6`;
решение `ADR-0002` проекта).

## Обязательный порядок

1. Проверь значимость решения: последствия переживают текущую задачу, дорого
   обратимы или задают правило для будущих решений. Предметный тест значимости
   своего вида даёт профильный навык (например, архитектурная значимость — в
   `ait-architecture`). Незначимое решение фиксируй короче (заметка в задаче)
   или не фиксируй вовсе.
2. Определи вид решения и журнал по правилам проекта «какое решение в какой
   журнал». Если подходящего журнала нет, предложи завести его — см. секцию об
   инициативе.
3. Собери пространство вариантов, включая крайние и неудобные точки. Не
   выдумывай варианты: если выбор безальтернативен, запись честно говорит об
   этом и объясняет почему.
4. Сверь с контекстом проекта — требованиями, ранее принятыми решениями,
   ограничениями и корпусом знаний, если он есть, — и варианты, и формулировку
   потребности в решении. Причина решения может лежать вне обсуждения, в котором
   оно прозвучало: например, потребность порождена ранее принятым архитектурным
   решением, а обсуждение дало только ограничения.
5. Оформи запись по подходящему шаблону (`references/decision-templates.md`).
   Независимо от шаблона запись покрывает минимум: контекст с формулировкой
   проблемы, рассмотренные варианты, решение с обоснованием, последствия и
   способ проверки.
6. Веди статус записи по единой модели: `Предложено`, `Принято`, `Устарело`,
   `Заменено`.
7. Перед передачей проверь запись контрольным списком качества
   (`references/decision-workflow.md`, секция «Контрольный список качества»).

## Решение до действия

Столкнувшись в ходе задачи со значимым выбором, не действуй по первому удобному
варианту:

1. Создай запись решения, выяви варианты, их достоинства и недостатки.
2. Сверь варианты с контекстом проекта (шаг 4 порядка выше).
3. Предложи решение и передай запись на проверку вторым взглядом; по замечаниям
   доработай.
4. Действуй только после принятия записи.

Способ принятия задают правила проекта: проверка вторым взглядом либо остановка
задачи для ручного одобрения человеком. Если ни один вариант не превосходит
остальные значительно, остановись и запроси решение человека.

## Проверка существующей записи или журнала

Если на входе уже существующая запись или журнал, не проходи шаги создания —
работай как проверяющий.

Для одной записи:

1. Проверь запись контрольным списком качества
   (`references/decision-workflow.md`, секция «Контрольный список качества»).
2. Проверь статус по единой модели и актуальность: если условие пересмотра
   наступило или внешние факторы изменились, предложи пересмотр — статус
   `Устарело` либо новая запись по общему порядку со статусом `Заменено` у
   старой.

Для журнала:

- реестр полон, ссылки ведут на существующие записи, записи не потеряны;
- у каждой записи статус по единой модели; у принятых указано условие
  пересмотра;
- решения, на которые опирается работа, но которых нет в журнале, — кандидаты на
  ретроспективную запись;
- правило «какое решение в какой журнал» существует и записи ему соответствуют.

Результат проверки оформи списком замечаний с привязкой к записям. Проверка
выявляет дефекты записи, но не меняет смысл принятого решения: изменение решения
— это пересмотр через владельца проекта.

## Инициативное предложение записей

Предлагай фиксацию решений, не дожидаясь прямого запроса:

- при настройке проекта и проработке структуры документации предложи завести
  подходящие журналы; первой записью предложи порядок принятия проектных решений
  — статусную модель и правило «какое решение в какой журнал»;
- при первом значимом решении, принятом заказчиком в диалоге, предложи завести
  журнал (если его нет) и записать решение;
- если работа опирается на значимое решение, которого нет в журнале, предложи
  ретроспективную запись с явной пометкой о её характере.

Отказ заказчика зафиксируй в состоянии проекта и не повторяй предложение без
нового запроса.

## Что читать дополнительно

- Для дисциплины записи (значимость, матрица развилки, статусы вариантов,
  готовность и завершённость, заполнение секций, ведение журнала, контрольный
  список качества) читай `references/decision-workflow.md`.
- Для каталога шаблонов записей (Nygard, MADR, Y-Statement, ISO 42010) со
  структурой и скелетами читай `references/decision-templates.md`.

Читай только те справки, которые нужны для текущей задачи.

## Границы

- Не подменяй решение владельца проекта выводом из корпуса или собственным
  предпочтением: навык оформляет и проверяет решения, а не принимает их.
- Не решай предметные вопросы вида: что значимо в архитектуре, документации или
  организации, определяет профильный навык соответствующей роли.
- Не оформляй запись, если данных недостаточно даже для отбрасывания слабых
  вариантов. Сначала предложи исследовательскую или аналитическую проверку.
- Не объединяй несвязанные решения в одну запись.
- Не включай в тело записи материалы, не влияющие на выбор.

## Опорные источники

Навык опирается на источники корпуса: сначала найди источник по `id` в
`knowledge/catalog.yml`, затем используй `knowledge/data/<slug>/source.yml`,
`knowledge/data/<slug>/items.yml` и связанные утверждения: `ADRG`, `SAHP`,
`RADR`.
