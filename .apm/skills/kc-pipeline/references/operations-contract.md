# Операционный контур корпуса

Этот договор дополняет `kc-pipeline` переносимым механизмом планирования и
обслуживания корпуса. Он не заменяет предметные навыки, не определяет адаптеры
и не принимает содержательные решения.

## Назначение

Контур даёт проекту четыре повторяемые операции:

- построить очереди по `workflow_stage`, карточкам единиц и артефактам рядом с
  ними;
- явно запустить зарегистрированные проектные команды одной стадии;
- пересобрать общие индексы единиц и утверждений из их владельцев;
- создать локальный отчёт конкретного запуска.

Средство запуска находится в
`scripts/run-corpus-operations.py`. По умолчанию оно только читает корпус и
пишет план в стандартный вывод:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py knowledge
```

## Настройки операций

Настройки не входят в обязательную раскладку корпуса. Если проекту они нужны,
он создаёт отдельный файл по образцу `assets/operations.yml` и передаёт его
параметром `--operations`.

```yaml
operations_version: 1
report:
  path: .local/reports/corpus-operations.md
normalized_artifacts:
  - normalized.md
  - message.md
  - stenogram.txt
stages:
  source_sync:
    commands:
      - id: source-sync
        argv: [python3, tools/sync-source.py]
        working_directory: .
        write_paths: [knowledge/data/example-source]
        required: true
```

`argv` — список аргументов без оболочки. `working_directory` и каждый путь из
`write_paths` задаются относительно корня проекта и не могут выходить за его
пределы. `write_paths` служит проверяемой границей ожидаемых изменений в Git.

Адаптер, его секреты, параметры доступа и обработка конкретного носителя
остаются в проекте-потребителе. Исполняемый реестр и формат его результата см.
в [договоре адаптеров](adapter-contract.md). Не храните в настройках токен,
cookie, пароль или закрытый адрес.

## Запуск команд

Команды не выполняются при обычном планировании. Для выбранной стадии нужен
явный параметр:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml \
  --stage source_sync --run-commands
```

Средство запуска передаёт `argv` напрямую, сохраняет код завершения и проверяет
изменённые пути через Git. Команда с ненулевым кодом завершения или изменением
за пределами `write_paths` останавливает обязательную стадию. Средство не
откатывает изменения команды: восстановление выполняет проектная команда или
следующий разрешённый запуск.

Для запуска адаптеров источников есть отдельный явный параметр
`--run-adapters`; он не запускает команды стадии `source_sync`.

## Предзапусковая проверка

Перед изменяющим запуском проект может добавить `--operational-check`.
Контур вызывает существующий валидатор раскладки, а не содержит второй сканер.
Валидатор рассматривает только `git ls-files` внутри корня корпуса и
исключает `*.local.*`, `*.tmp.*`, `local/`, `.local/` и каталоги
`*.local` прежде чтения. В отчёте остаются только путь, номер строки и вид
находки, поэтому найденное значение не копируется в локальный отчёт.

Результат разделён на ошибки договора, блокеры доступа (`access-secret`,
`credentialed-url`), предупреждения качества (`personal-data`) и очереди
корпуса. Открытый контакт в метаданных источника фиксируется отдельно и сам по
себе не блокирует запуск. Ложное срабатывание разрешается подавить только
правилом с причиной:

```text
... --operational-check --operational-policy knowledge/operational-check.yml
```

Шаблон правила находится в
`kc-inventory/assets/operational-check.yml`. Подавление меняет
классификацию, но не выводит чувствительное значение и не заменяет решение о
публикации.

## Индексы и восстановление

После успешной синхронизации пересоберите производные индексы:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --rebuild-indexes
```

Новые файлы индексов строятся полностью до записи; каждый из них создаётся во
временном файле и заменяется без появления частично записанного файла. Если
запуск прервался между заменами, карточки источников остаются владельцами
данных, а следующий запуск с `--rebuild-indexes` восстанавливает согласованную
пару общих индексов. После восстановления нужно выполнить проверку корпуса,
заданную проектом.

## Локальный отчёт

Отчёт описывает конкретный запуск: размер очередей, первые элементы каждой
очереди, коды завершения команд и число записей в пересобранных индексах. Он не
содержит содержательных выводов или отчёта влияния.

Запись отчёта происходит только по явному запросу:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --write-report
```

Путь `report.path` должен вести в неотслеживаемый локальный слой. Не добавляйте
такой отчёт в Git.

## Очереди

Средство использует переносимые очереди `content_selection`, `fetch`,
`transcribe`, `normalize`, `statements`, `source_check` и `human_decision`.
Штатная стадия `indexed` не считается неподдерживаемой:

- единица обычного источника без выбранного объёма обработки попадает в
  `content_selection`;
- единица с `processing_scope: selected_fragments`, `full` или
  `full_redacted` попадает в `fetch` для точечного получения;
- единица источника со `storage_strategy: index_only` без выбранного объёма
  обработки не образует массовую очередь: обновлённый индекс завершает
  штатный проход такого источника.

Неподдерживаемая стадия и `blocked` попадают в `human_decision`, а не получают
выдуманный переход. Содержательный отбор должен завершиться явным решением:
выбрать единицу для точечного получения, отклонить её с причиной или отправить
в `human_decision` только вопрос, который действительно требует решения
человека.

Имена нормализованных артефактов настраиваются через `normalized_artifacts`.
Сырая `transcript.txt` не считается нормализованным артефактом: она оставляет
единицу в очереди нормализации.
