# Навык: kc-validation

## Назначение

Этот навык задаёт порядок комплексной проверки корпуса знаний проекта на
формальные ошибки, полноту обработки первичных данных, соответствие источников и
извлечённых утверждений специфике проекта, а также на отсутствие внутренних
противоречий.

Проверка по умолчанию является только чтением: навык фиксирует ошибки,
ограничения и следующие маршруты, но не создаёт и не обновляет договор структуры
корпуса.

Навык нужен для того, чтобы проект мог поддерживать качество и надёжность
корпуса знаний как основания для принятия решений, проектирования и
документирования.

## Когда применять навык

Навык применяется:

- после внесения изменений в корпус знаний;
- если пользователь попросил проверить корпус знаний.

Навык не применяется для единичной проверки одного файла или одного источника,
если это не часть общей проверки корпуса.

## Входные данные

Для применения навыка должны быть доступны:

- проектный договор, манифест или локальные правила структуры корпуса знаний;
- перечень источников и их статусы;
- нормализованные представления первичных данных;
- извлечённые утверждения;
- производные документы проекта;
- сведения о специфике проекта (цель, область применения, ограничения).

Если этих данных недостаточно, ограничение должно быть зафиксировано явно.

## Результат применения навыка

Результатом должен быть отчёт пользователю о проверке корпуса знаний, по
которому понятно:

- какие формальные ошибки найдены и где именно;
- какие источники не доведены до конца цепочки обработки;
- какие источники или утверждения не соответствуют специфике проекта;
- какие внутренние противоречия выявлены;
- насколько корпус надёжен как основание для проектной работы.

В отчёте не надо выводить лишние сведения, такие как списки проверенных объектов
или объекты без проблем.

В конце отчёта предложи начать устранение проблем по одной, начиная с первой.

## Порядок применения

### 1. Проверить формальную целостность корпуса

Нужно проверить структуру и состав корпуса на соответствие проектному договору,
а не универсальному имени каталогов. Сначала найди договор структуры:
`corpus.yml`, `catalog.yml`, явно названный проектный манифест или проектные
правила структуры.

`AGENTS.md` может объявлять путь корпуса и обязанность его использовать, но сам
по себе не является договором файловой структуры. README внутри папки корпуса
тоже не считается договором структуры и не должен требоваться как опорный файл
корпуса.

Если проект уже объявляет, что использует корпус знаний, но договор структуры не
найден или выбранная папка не содержит минимальных опорных файлов корпуса,
зафиксируй это как формальную ошибку валидации, а не только как ограничение.
Переносимые критерии проверяемого корпуса можно использовать как стартовую
схему для диагностики, но нельзя объявлять корпус структурно валидным без
локального договора или минимальной стартовой структуры. Наблюдаемая файловая
раскладка является только свидетельством текущего состояния, а не договором:
не синтезируй из неё `corpus.yml`, `catalog.yml` или проектные правила и не
считай такой синтез подтверждённым договором.

Если проект перешёл на переносимую структуру, но в корне корпуса остались
старые слои `inventory/`, `primary/`, `normalized/`, `statements/` или
`reports/`, считай это незавершённой миграцией. Та же ошибка сохраняется, если
`corpus.yml` закрепляет эти папки как `legacy_*` или как отдельные активные
слои. Они должны быть перенесены, вынесены в локальный слой или названы
блокером владельца проекта до сообщения об успешной проверке.

Если договор структуры отсутствует или сомнителен, первая точка исправления -
выбрать или подтвердить владельцем проекта договор корпуса через отдельный
маршрут `kc-inventory`, затем повторить проверку. Не исправляй это внутри
валидации.

Если корпус ещё не заявлен проектом и пользователь просит только оценить
возможное место для будущего корпуса, отсутствие договора можно фиксировать как
ограничение, а не как ошибку существующего корпуса.

Подробный чеклист формальной целостности см. в
`references/corpus-checklist.md`.

Зафиксируй все найденные формальные ошибки в отчёте.

### 2. Проверить полноту цепочки обработки первичных данных

Для каждого источника проверь проход по всей цепочке обработки.

Подробный чеклист полноты цепочки см. в `references/corpus-checklist.md`.

Зафиксируй источники, которые не прошли полную цепочку обработки.

### 3. Проверить соответствие источников специфике проекта

Для каждого источника проверь, относится ли он к проекту.

Критерии соответствия проектной специфике см. в
`references/corpus-checklist.md`.

Зафиксируй источники, которые не соответствуют специфике проекта или требуют
перепроверки.

### 4. Проверить соответствие извлечённых утверждений специфике проекта

Для каждого файла извлечённых утверждений проверь содержание.

Критерии проверки утверждений см. в `references/corpus-checklist.md`.

Если у утверждения указано поле `kind`, оно должно принадлежать словарю
`fact`, `observation`, `inference`, `limitation`. Значения этого словаря не
должны использоваться как `status`: статус отражает степень проверки, а вид —
природу утверждения.

Зафиксируй утверждения, которые не соответствуют специфике проекта или извлечены
с ошибками.

### 5. Проверить корпус на внутренние противоречия

Сопоставь утверждения из разных источников между собой.

Подробные типы противоречий см. в `references/corpus-checklist.md`.

Для каждого противоречия зафиксируй:

- какие утверждения или источники противоречат;
- в чём именно заключается противоречие;
- насколько противоречие существенно для проекта;
- требуется ли решение человека для разрешения.

### 6. Проверить полноту извлечения и слой согласования понятий

Для содержательного источника проверь карту охвата: каждая структурная единица
имеет статус, нет молчаливых пропусков, нет признаков поверхностного извлечения.

Если в проекте есть слой согласования понятий, проверь целостность его ссылок:
`defined_by` ведёт на существующие утверждения, `covered_in` — на существующие
файлы продукта, у записи есть основная форма и источник её выбора, разрывы
связаны с бэклогом, слой не хранит контент.

Критерии полноты извлечения и слоя согласования понятий см. в
`references/corpus-checklist.md`.

## Что читать дополнительно

- Для развёрнутого чеклиста комплексной проверки корпуса см.
  `references/corpus-checklist.md`.

## Что считается ошибкой применения навыка

- формальная ошибка пропущена из-за невнимательности;
- проверка создаёт, обновляет или принимает синтезированный из текущих папок
  договор структуры;
- источник считается прошедшим обработку без проверки всех файлов;
- утверждение принято как соответствующее проекту без проверки связи с
  источником;
- противоречие сглажено вместо явной фиксации;
- извлечение из содержательного источника принято без карты охвата или с
  единицами без статуса;
- битые ссылки слоя согласования понятий не замечены;
- проверка остановлена на одном слое без перехода к другим;
- отчёт не даёт явного перечня проблем и рекомендаций;
- слабость корпуса скрыта вместо явной фиксации.

## Связь с другими элементами продукта

Этот навык должен применяться вместе:

- с принципом корпуса первичных данных;
- с ролью `kc-inventory`;
- с ролью аналитика для разбора противоречий;
- с навыком приёма первичных данных в корпус;
- с навыком нормализации первичных данных;
- с навыком извлечения утверждений из данных;
- с контрольным слоем, если проверка выявляет существенные проблемы корпуса;
- с навыком аналитического разбора для оценки влияния противоречий.
